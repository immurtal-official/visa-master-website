# Visa Master 用户画像总结

## 1. 产品定位前提

Visa Master 的核心产品不是“帮用户搜索签证攻略”，而是把用户的签证申请需求转化为一个可提交、内部一致、经过机器检查和人工复核的材料包。

典型任务：

> 用户说：“我住在成都，想申请西班牙旅游签。”
> 系统输出：官方来源、申请表说明、材料清单、行程、在职/准假证明模板、cover letter、财务说明、提交索引和警示说明。

当前 V1 beachhead：

> 中国公民，在中国境内，从成都领区申请西班牙申根旅游签证；申请人为在职人员，出行目的为个人旅游。

V2 方向（相邻路线扩张，见 PRODUCT.md §4）：

> 下一个申根目的地和/或下一个中国领区，复用已沉淀的官方要求缓存与表单映射资产。美国 B1/B2 属于更远的 V3/后续探索，不进入当前画像讨论。

贯穿全文的另一个前提（长期指令，2026-08-09）：**手机与电脑地位并重，移动优先只指构建顺序。** 发现端以手机为主（小红书/微信是获客渠道），但发现设备不决定完成设备——全程手机、全程电脑、手机发现电脑完成、电脑上开始再用手机拍材料，四种都是真实且受支持的组合，跨设备续填是被设计出来的正常流程。两端各承载 100% 功能，任何一端都不是另一端的降级版本。详见[移动端平权](../guidelines/mobile-parity-zh.md)。下文各画像的能力特征据此按"两端皆可"描述。

## 2. 核心用户画像

### Persona A：自助型年轻/中青年申请人

**年龄段**：20–40 岁

**典型身份**：

- 在职白领：互联网/科技/金融/教育/医疗等行业从业者
- 刚工作几年、能开出在职与准假证明的年轻人
- 有个人出境旅游需求的人

> **边界说明：** V1 仅服务在职申请人——唯一验证过的模板集是在职形态（在职/准假证明 + 工资流水财务叙事）。学生（需在读证明 + 资助说明模板变体）不在 V1 验收范围，见 §3 后续人群。探亲、短期商务、会议参会是相邻需求、后续路线：路线查询会把这些目的导向 waitlist，而不是当作已支持路径。

**能力特征**：

- 手机与电脑都能胜任：能用手机完成分步表单、拍照上传材料、在系统浏览器完成支付宝支付；也可能整段改用电脑（拖拽上传、扫描件、大屏核对）。
- 大概率从小红书/微信内打开产品；此后可能全程留在手机上，也可能换到电脑上收尾，产品不假设其中任何一种。
- 愿意自己上传材料、核对信息。
- 不一定懂签证规则，但愿意跟着系统一步一步做。

**核心需求**：

- 不想花很多时间查官方要求。
- 不想在小红书、知乎、旅行社攻略和官网之间反复比对。
- 想知道自己到底该交什么材料。
- 想减少表格、行程、在职证明、银行流水说明之间的信息不一致。

**付费理由**：

- 几百元可以省掉大量时间。
- 比旅行社便宜。
- 比自己照着网上攻略做更稳。
- 交付的是完整材料包，而不是一篇泛泛攻略。

**主要顾虑**：

- AI 会不会乱编？
- 我的护照和银行流水安全吗？
- 出错了谁负责？
- 系统生成的材料真的能用吗？

---

### Persona B：中产/准中产的高确定性用户

**年龄段**：30–55 岁

**典型身份**：

- 已工作多年，有稳定收入和家庭安排的在职人员。
- 准备个人或夫妻/家庭的出境旅游。（商务短停、探亲访友是相邻需求、后续路线，V1 不承接，路线查询导向 waitlist。）
- 可能已经被旅行社报价劝退。

**能力特征**：

- 两端都要走得通：能在手机上完成分步表单、拍照上传材料并在系统浏览器完成支付宝支付；这一人群也常有办公或家用电脑，习惯在电脑上处理"正事"（网银导出流水、打印签字），因此电脑路径必须同样完整。
- 不一定喜欢折腾复杂网站。
- 希望流程像“报税软件”或“在线保险申请”一样清楚。

**核心需求**：

- 知道每一步为什么要填。
- 知道材料缺什么。
- 知道自己的信息是否前后一致。
- 知道签证中心、领区、表格、费用、预约入口等信息来自哪里。

> **边界说明（夫妻/家庭同行）：** V1 的一致性校验以**单份申请**为边界，不做跨申请检查——夫妻两份申请之间的日期、行程、酒店是否互相吻合，V1 不校验，需用户自行核对，产品文案应如实说明。低成本缓解方案（第二份 intake 从已有申请克隆行程级数据：日期、路线、酒店）是 Phase 2 候选项。

**付费理由**：

- 他们不是完全没有钱，而是不想为普通旅游签证付旅行社高价。
- 相比纯 DIY，愿意为“省心、可靠、可解释”付费。
- 价格落在几百元量级时，心理上更像“专业辅助工具”，不是高价代理。（¥199–399 是仅限内部讨论的定价区间；对外只展示单一价格，工作占位 ¥299，上线前最终定价。）

**主要顾虑**：

- 会不会最后还是要我自己做很多？
- 会不会生成的东西不符合领馆要求？
- 会不会把我的个人信息泄露？
- 是否有人工帮我看？

---

### Persona C：代办型家庭成员

**年龄段**：25–45 岁为主

**典型身份**：

- 子女帮父母办理旅游签证。
- 配偶帮另一方填写资料。
- 成年子女帮家庭成员整理材料。

**实际申请人**：

- 可能是父母、配偶或其他亲属。
- 真实申请人未必熟悉手机操作，由操作者代为完成流程。

**V1 服务边界**：

- V1 支持本人申请和**简单代他人申请**：一位操作者 + 一位申请人。数据结构与文案始终区分“账号使用者（操作者）”与“实际申请人”，绝不混用。
- 上传任何第三方材料前，先完成**被申请人（实际申请人）的明确同意**采集——PIPL 合规要求，不是可选项。
- 申请人须为在职人员（见 Persona A 边界说明与 §3）。因此“帮退休父母办签证”这一典型场景 V1 暂不可交付：路线/intake 入口在**付款前**明确拦截退休申请人；退休模板变体（退休证明 + 养老金/存款财务叙事）是最近的扩展方向。V1 能服务 Persona C 的情形是申请人本身在职，例如帮在职配偶代办。
- **多申请人/家庭成员分开管理是明确的 V2+（Phase 4）能力**：V1 不提供，也不在任何文案中暗示提供。

**能力特征**：

- 操作者两端都熟练：能替申请人完成分步表单、拍照上传和支付宝支付，也可能在电脑上集中整理亲属发来的材料。
- 材料来自另一个人（常常是微信里发来的照片），需要反复询问，中断、分次、跨设备填写是常态。
- 依赖分步保存与草稿恢复（服务端持久化，见[移动端平权](../guidelines/mobile-parity-zh.md)）。

**核心需求**：

- 支持“我帮别人办”：一位操作者替一位申请人走完全程。
- 支持分步保存，不要求一次填完。
- 对材料用途解释清楚，既方便操作者向亲属索要材料，也支撑向被申请人说明用途并取得同意。

**付费理由**：

- 家庭成员自己办很耗时间。
- 找旅行社又贵又不透明。
- 系统化收集信息可以减少来回沟通。

**主要顾虑**：

- 亲属材料不齐怎么办？
- 以别人的名义上传材料是否合规、对方是否知情？（产品以显式的被申请人同意环节回应。）
- 帮父母办：父母已退休怎么办？（V1 在付款前明确告知暂不支持并登记 waitlist，而不是收钱后失败。）

---

### Persona O：创始人兼审核员（内部操作者）

V1 唯一的内部用户：创始人本人承担每个材料包交付前的人工复核（见 PRODUCT.md §7——人工审核门是刻意且永久的）。

**目标**：

- 单包复核耗时以分钟计，可持续、可预估。
- 错误捕获率：机器 QA 之后仍能拦下事实性与一致性问题。
- 补材料周转快：从发现问题到用户收到结构化、可执行的驳回理由，越短越好。

**工作界面**：

- 复核界面是 `apps/web` 内的角色门控路由（开发计划：`/admin/review`），不是独立的后台应用。
- 路线规则保持在代码中（ADR-002）；管理端的“路线”页面是只读运维视图（代码中的在线路线、要求缓存快照时间、模板版本）。
- 手机上可完成三件事：查看带 SLA 计时的审核队列、阅读一份申请（含材料包预览图）、创建并发送补材料请求；并排深度比对保持桌面优先。

## 3. 非核心与后续人群

### 暂时不优先服务的人群

| 用户类型 | 暂不优先原因 |
|---|---|
| 手机和电脑都无法自助完成流程的申请人 | V1 是线上自助流程，两端功能对等——只用电脑、不惯用手机的申请人是**被服务的客户**；真正超出 V1 的是需要线下服务、电话服务或全程人工代办的用户 |
| 学生申请人 | 缺少在读证明 + 资助说明模板变体，不在 V1 验收范围（唯一验证过的模板集是在职形态）；路线/intake 入口在付款前拦截；属最近的模板变体扩展之一 |
| 退休申请人 | 缺少退休证明 + 养老金/存款财务叙事模板变体；同样在付款前拦截；属最近的模板变体扩展之一（见 Persona C 服务边界） |
| 极低预算用户 | 可能更倾向免费攻略或模板，不愿付费 |
| 高净值复杂签证用户 | 可能需要律师、移民顾问或高端旅行社，不适合 V1 标准化材料包 |
| 高风险拒签背景用户 | 涉及复杂解释、拒签史、敏感职业、资产证明困难，V1 不应承诺解决 |
| 企业批量差旅用户 | 可能是后续 B2B 机会，但不是 V1 的最小验证目标 |

### 相邻需求、后续路线

探亲、商务、会议参会是真实存在的相邻需求，但 V1 只做个人旅游：路线查询把这些目的作为不支持分支处理，引导进轻量 waitlist 登记，绝不作为已支持路径展示。学生与退休申请人的模板变体是最近的人群维度扩展；探亲/商务/会议是目的维度的后续路线。

## 4. 用户真正购买的价值

用户表面上买的是“签证材料包”，实际购买的是：

1. **确定性**：知道自己属于哪个领区、该交什么材料、去哪里提交。
2. **一致性**：表格、行程、证明、说明信中的日期、城市、单位、收入等信息一致。（V1 的一致性以单份申请为边界；跨申请一致性见 Persona B 的边界说明。）
3. **省时间**：减少搜索、比对、复制粘贴和反复修改。
4. **可解释性**：每个要求能追溯到官方来源，而不是来自模糊攻略。
5. **心理安全感**：知道有人工复核，而不是完全交给 AI。
6. **性价比**：比旅行社便宜，比免费攻略可靠。

## 5. 用户核心焦虑

| 焦虑 | 产品需要如何回应 |
|---|---|
| 怕拒签 | 不承诺过签，强调减少材料错误和不一致 |
| 怕 AI 编造 | 强调官方来源、来源引用、人工复核 |
| 怕隐私泄露 | 说明数据用途、保留时间、删除方式、访问权限 |
| 怕流程复杂 | 分步骤、保存草稿、清楚进度、少字段一屏 |
| 怕材料缺失 | 用 checklist、缺失提醒、补材料流程 |
| 怕花钱没效果 | 展示交付样例、价格、交付内容、退款/限制说明 |

## 6. 对产品设计的直接启示

### 6.1 网站视觉不能过度“AI 炫技”

签证是高信任事项，用户上传的是护照、银行流水、在职证明等敏感材料。视觉应该可靠、清晰、专业，而不是像娱乐型 AI demo 或 crypto 项目。

### 6.2 首页第一屏必须解释清楚“你到底交付什么”

用户第一眼应该看到：

- 我填写一次信息。
- 系统查询当前官方要求。
- 自动生成互相一致的材料包。
- 人工复核后交付。

### 6.3 Intake form 要像“报税软件”而不是普通网页表单

关键是：

- 一步一步问。
- 每一步解释为什么问。
- 可保存、可回来继续。
- 错误提示具体。
- 显示进度。

### 6.4 需要支持“为他人申请”

V1 支持简单代他人申请：一位操作者 + 一位申请人。语言和数据结构上只建模两个角色，且绝不混用：

- 账号使用者（操作者）
- 实际申请人

上传第三方材料前须采集被申请人的明确同意（PIPL 要求）。付款人、联系人不在 V1 建模——它们是 V2+ 候选角色，等到有真实功能需要（如代付、多渠道通知）时再引入。多申请人/家庭账户是 V2+（Phase 4）能力。

### 6.5 用户不一定买“AI”，用户买“更稳的材料准备流程”

AI 应该被表达为后台能力，而不是品牌主角。更好的表达是：

> 官方来源检索 + 材料自动生成 + 一致性校验 + 人工复核。

### 6.6 两端并重，跨设备是常态

整条旅程——intake、材料上传、支付、进度、材料包查看与下载——在手机和电脑上都必须完整可走，体验彼此同级。发现端以手机为主，但完成端由用户自己决定。以下四件事必须当作显式设计问题对待，而不是把一端的方案等比缩放到另一端：

- **拍照采集**：拍照/相册/文件是手机端首要上传路径，配即时质量把关与多页页组。
- **微信 webview 内的支付接力**：逃生舱引导 + 鉴权接力到系统浏览器完成支付宝支付，支付状态由 webhook 驱动。
- **材料包交付两端各有形态**：浏览器内查看器与打印合订 PDF 在两端通用；手机端以邮件发链接为主、zip 次要，电脑端可直接下载、直接打印、在本地 Word/WPS 里编辑模板。
- **电脑端的原生优势要被用上**：多文件拖拽、扫描件作为一等来源、并排比对、一屏看全文件树、键盘走位——这些不是"顺便支持"，是电脑端存在的理由。

用户随时可以换设备：草稿、上传件和支付状态都在服务端，任一设备都能从离开的那一步精确续上；Persona C 的操作者尤其会在手机收材料、电脑上汇总之间来回切。细节规范见[移动端平权](../guidelines/mobile-parity-zh.md)（§3.11 电脑端能力、§3.12 跨设备接力），此处不重复。
