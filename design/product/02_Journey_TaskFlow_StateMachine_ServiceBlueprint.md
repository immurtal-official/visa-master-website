# 用户旅程、核心任务流、状态机、服务蓝图：区别与 Visa Master 版本

## 1. 这几个概念为什么看起来重复？

你感觉它们重复是对的，因为它们都在描述“用户如何从需求走到交付”。

但它们的观察角度不同：

| 概念 | 主要视角 | 关注问题 | 产出对象 |
|---|---|---|---|
| 用户旅程图 | 用户体验视角 | 用户每一步想什么、怕什么、看到什么 | 产品、设计、文案 |
| 核心任务流 | 操作路径视角 | 用户完成一个目标需要点击/填写哪些步骤 | 产品、前端、UX |
| 状态机设计 | 系统实现视角 | 系统有哪些状态、什么事件触发状态变化 | 后端、工程、产品 |
| 服务蓝图 | 前后台协作视角 | 用户前台动作如何触发后台 AI、人工审核、通知、交付 | 产品、运营、工程 |

一句话区分：

> 用户旅程图讲“用户怎么感受这件事”；核心任务流讲“用户怎么操作”；状态机讲“系统怎么判断当前进度”；服务蓝图讲“前台和后台如何一起完成服务”。

---

## 2. 对 Visa Master 来说，它们确实应该合并理解

Visa Master 是一个工作流产品，不是普通内容网站。用户不是简单浏览信息，而是经历一个完整服务流程：

1. 选择签证路线。
2. 填写个人和旅行信息。
3. 上传材料。
4. 支付。
5. 系统/AI 处理。
6. 机器 QA。
7. 人工审核。
8. 如被驳回，按结构化原因补齐后重新提交（触发新一次完整生成）。
9. 在线查看并获取材料包。
10. 按 checklist 提交。

这条链路在手机和电脑上都要能完整走完，用户也可以中途换设备（草稿、上传件与支付状态都在服务端，任一设备从离开处精确续上）。发现多始于小红书/微信的 in-app webview，但完成端由用户决定。两端行为都是每个环节完成定义的一部分——具体需求见[移动端平权](../guidelines/mobile-parity-zh.md)（§3.11 电脑端能力、§3.12 跨设备接力），本文只在各环节点名机制。

所以这几个文档会天然相似。合理做法不是强行分开，而是：

- 用 **用户旅程图** 描述体验和心理。
- 用 **核心任务流** 指导页面和交互。
- 用 **状态机** 指导数据库和后端逻辑。
- 用 **服务蓝图** 指导 AI、人工审核和运营流程。

## 3. Visa Master 用户旅程图

V1 的旅程以已验证的滩头路线为背景：**成都领区 → 西班牙申根个人旅游签**（见 [PRODUCT.md](../../PRODUCT.md) §4）。探亲、商务、会议是相邻需求、后续路线；美国 B1/B2 是更远的 V3/后续探索（V2 相邻路线扩张指的是下一个申根目的地/下一个领区）——旅程里它们都只以“暂不支持 → 等待名单”的形态出现，不是被服务的路径。

### 阶段 1：产生需求

**用户行为**：

- 想去西班牙/欧洲旅游。
- 在手机上的小红书搜索“西班牙签证 攻略”，或搜索“西班牙签证 成都 旅游签 材料”。
- 比较旅行社、攻略笔记、官网。

**用户心理**：

- 不确定自己该看哪个官网。
- 担心领区、签证中心、材料要求不同。
- 担心表格填错。

**产品机会**：

- 首页直接解释：按城市、目的地、签证类型生成材料包。
- 强调官方来源和人工复核。
- 落地页在小红书/微信 webview 内完整可用（发现即第一会话场景）。

---

### 阶段 2：判断是否适合使用 Visa Master

**用户行为**：

- 进入首页。
- 查看支持路线、价格、交付内容、样例。
- 查看隐私和免责声明。

**用户心理**：

- 这个是不是旅行社？
- AI 会不会乱写？
- 能不能真的生成可用材料？
- 我的隐私安全吗？

**产品机会**：

- 明确说明：不是代替领馆决定，不承诺过签。
- 明确说明：帮助准备材料、减少不一致、引用官方来源、人工复核。
- 展示样例包目录（webview 内以预渲染页面图片浏览，不依赖下载）。

---

### 阶段 3：开始申请

**用户行为**：

- 选择所在城市/常住地。
- 选择目的国家。
- 选择签证类型。
- 选择预计出行日期。
- 申请人国籍默认为中国公民，仅在例外情况下询问。

**用户心理**：

- 我是不是选对了路线？
- 成都到底归哪里管？
- 我能不能申请这个类型？

**产品机会**：

- 用路线识别器判断是否支持：支持的路线是显著的主路径；不支持时给出“暂不支持 → 加入等待名单”的明确次要分支（等待名单是轻量留资记录，不会创建申请）。
- V1 只服务在职申请人（唯一经过验证的模板集是在职形态）：在读与退休申请人在路线/信息采集入口即被识别并明确告知——在付款之前，而不是之后。

---

### 阶段 4：填写 intake form

**用户行为**：

- 填写个人信息、护照信息、工作信息、收入、储蓄、旅行计划。
- 填写是否独自旅行、是否有同行人、是否有人资助。
- 中途被打断（回聊天消息、切换应用），回来后从上次的位置继续。

**用户心理**：

- 为什么要问这个？
- 我不知道怎么填怎么办？
- 如果填错会不会影响签证？

**产品机会**：

- 每个敏感字段旁边有解释。
- 明确“用于生成材料，不会自动提交给领馆”。
- 关键字段做一致性提示——由 `packages/core` 中的确定性 zod/规则代码完成（ADR-002），付款前不发生任何 LLM/OCR 调用。
- 草稿每步自动保存到服务端并可精确恢复；在移动端，被打断才是中位数会话（一屏一问、自动保存等具体要求见[移动端平权](../guidelines/mobile-parity-zh.md) §3.3）。

---

### 阶段 5：上传材料

**用户行为**：

- 手机端：拍摄或从相册/文件选择护照、银行流水、在职证明、户口/身份证等材料（拍照采集是手机端首要路径）。电脑端：多文件拖拽、扫描件多页 PDF 作为一等来源；也可扫码调用手机当相机，拍摄结果直接进入电脑端会话。
- 多页材料（如银行流水）逐页拍摄，组成有序页组。
- 根据 checklist 补充缺失文件。

**用户心理**：

- 上传这些安全吗？
- 哪些必须上传，哪些可以后补？
- 银行流水要几个月？

**产品机会**：

- 材料清单按“必须 / 推荐 / 可选 / 视情况”分组。
- 对每项材料解释用途。
- 上传即刻做拍摄质量把关（模糊/反光/分辨率），当场提示重拍；上传分块可断点续传。
- 逐项状态只声称真正检查过的东西：客户端格式/大小/页数 + 拍摄质量——写“格式检查通过”，绝不写“材料已审核”。
- 给隐私说明和删除说明。

---

### 阶段 6：支付与提交

**用户行为**：

- 确认服务范围。
- 支付（V1：支付宝，经 Stripe，在系统浏览器中完成；微信 webview 内经逃生舱引导 + 鉴权接力跳出）。
- 正式提交生成。

**用户心理**：

- 付了钱会得到什么？
- 多久能交付？
- 如果材料不够怎么办？

**产品机会**：

- 付款前明确交付内容与单一价格。
- 明确“不承诺签证结果，只提供材料准备与一致性检查”。
- 明确预计交付时间和补材料机制（含被驳回后重新生成的时间预期）。
- 已支付状态由 webhook 驱动，跳转是否顺利回跳都不影响；任何页面重开都会重新拉取到已支付状态。

---

### 阶段 7：AI/系统生成材料包

**用户行为**：

- 提交后即可关掉页面——进度完全异步，不假设有一个盯着的浏览器标签页。
- 随时经任何链接重入进度页查看当前阶段。

**用户心理**：

- 系统现在在做什么？
- 是不是卡住了？
- 生成的东西可靠吗？

**产品机会**：

- 显示进度阶段：官方来源核对中 → 材料生成中 → 一致性检查中 → 人工复核中（约 10 分钟生成 + 以小时计的人工复核）。
- 不需要实时展示全部内部细节，但要让用户知道流程在推进。
- 状态变更经短信通知（V1；邮件为辅），用户不必守着页面。

---

### 阶段 8：人工审核

**用户行为**：

- 等待人工审核（状态变化经短信触达）。
- 如被驳回，收到列明具体原因的补材料请求。

**用户心理**：

- 人工审核是不是认真看？
- 为什么还要补材料？

**产品机会**：

- 把人工审核作为信任机制，而不是延迟。
- 驳回原因结构化且具体：缺什么、为什么缺、如何补。
- 补材料闭环完全移动原生：通知深链 → 手机拍摄补件 → 重新提交（见[移动端平权](../guidelines/mobile-parity-zh.md) §3.7）；页面明确预期「重新生成约需 10 分钟」。

---

### 阶段 9：交付材料包

**用户行为**：

- 在浏览器内材料包查看器中逐文件、逐页查看（含微信 webview 内）。
- 获取打印合订 PDF（“发给打印店的文件”），或把材料包链接发到邮箱。
- 查看 Start Here checklist，按顺序打印、签字、预约或递交。

**用户心理**：

- 这些材料怎么用？
- 哪些要打印？
- 哪些要签字？
- 哪些只是说明？

**产品机会**：

- 文件夹结构清楚。
- 第一个文件必须是 Read-first master checklist。
- 提供提交顺序、打印/签字提醒、来源警示。
- 交付不依赖下载：在线查看器（逐文件预渲染页面预览，DOCX 配 PDF 转制版）+ 打印合订 PDF + 邮件链接是主路径，zip/逐文件下载是次要路径（见[移动端平权](../guidelines/mobile-parity-zh.md) §3.8）。

## 4. Visa Master 核心任务流

### 主任务流：生成签证材料包

```text
进入首页
→ 选择“开始准备签证材料”
→ 选择当前居住城市/领区
→ 选择目的国家
→ 选择签证类型
   （申请人国籍默认中国公民，仅例外时询问）
→ 系统判断是否支持路线
   ├─ 支持（主路径，视觉上显著）→ 创建申请草稿
   └─ 暂不支持 → 加入等待名单（次要分支，流程到此为止）
→ 填写 intake form（每步自动保存到服务端，中断后可精确续填）
→ 上传必要材料（拍照/相册/文件，多页页组，即时质量把关，断点续传）
→ 系统提示缺失/矛盾信息（packages/core 中的确定性规则，无 LLM）
→ 用户修正
→ 支付（微信内经逃生舱到系统浏览器；webhook 确认已支付）
→ 提交生成
→ 系统生成材料包（约 10 分钟，进度异步，可关页）
→ 机器 QA + 服务端校验
→ 人工复核
   ├─ 批准 → 交付
   └─ 驳回（结构化原因）→ 补材料后重新提交（= 新一次完整生成）
→ 在浏览器内查看材料包
→ 查看 checklist 并准备递交
```

### 补材料任务流

```text
收到短信/邮件通知（驳回及原因）
→ 打开申请详情页（深链，必要时鉴权接力）
→ 查看结构化原因清单：缺什么、为什么、如何补
→ 用手机拍摄/上传新文件，或修改 intake 字段
→ 重新提交
→ 系统入队新一次完整生成（约 10 分钟，消耗真实生成成本，
   受 max_attempts 上限约束；材料包信用保留，不再收费）
→ 回到机器 QA 与人工复核
```

两点必须写进产品预期，而不是藏在实现里：

- **重新提交不是“重新检查”**——它是一次完整的重新生成。页面文案明确写「重新生成约需 10 分钟」。
- 对于简单笔误（一个日期、一个拼写），运营人员可在复核界面直接人工修正后放行，不必整包重跑——这是运营路径，不是用户路径。

### 代他人申请任务流

V1 支持本人申请与**简单代他人申请**：恰好一名操作者（账号持有人）+ 一名申请人。

```text
创建申请
→ 选择“我为他人申请”
→ 填写实际申请人信息（申请人 ≠ 账号持有人，数据模型中分开建模，文案中绝不混用）
→ 上传前采集被申请人的明确授权同意（PIPL 要求）
→ 上传申请人材料
→ 系统在所有文档中使用实际申请人信息
```

边界：付款人/联系人角色 V1 不建模（V2+ 候选，与真实功能绑定再立项）；多申请人/家庭成员分开管理明确是 V2+/Phase 4。同行人（夫妻/家庭）的跨申请一致性检查 V1 没有——第二份申请可克隆行程级数据（日期/路线/酒店）是 Phase 2 候选。

## 5. Visa Master 状态机设计（映射，而非发明）

本文档不发明状态名。权威词汇已在两层定稿，产品文档的职责是把用户旅程**映射**上去：

- **案件生命周期（用户可见）**：[architecture v0.4](../../doc/architecture-v0.4-zh.md) A 章的 `case_state` 枚举——`draft, intake, queued, running, awaiting_user, qa_pending, review_pending, delivered, failed, timeout, cancelled`。**V1 实现其中不含 `awaiting_user` 的子集**：没有运行中途的交互，确定性信息采集把所有问题前置到 intake。
- **作业层**：[开发计划](../../doc/platform-and-dev-plan-zh.md) B.1 的 `jobs.status = queued|leased|running|awaiting_review|delivered|failed|expired`；运行内部阶段记录在 `progress` JSONB（`intake → research → documents → qa → awaiting_review`）。
- **支付不是状态**：它是入队前检查的守卫/信用（`pack_credits`，webhook 翻转）。状态机里没有“已付款”一格。

### 5.1 V1 状态映射表

| 案件状态（A 章） | 作业层（B.1 status / progress.stage） | 用户可见文案 |
|---|---|---|
| `draft` | —（尚无作业） | 草稿中 |
| `intake` | — | 正在填写资料 |
| `queued` | `queued`（支付守卫通过后入队） | 排队等待生成 |
| `running` | `leased`/`running`，stage=`research` | 官方来源核对中 |
| `running` | `running`，stage=`documents` | 材料生成中 |
| `qa_pending` | `running`，stage=`qa`（产物收集 + 服务端校验） | 一致性检查中 |
| `review_pending` | `awaiting_review` | 人工复核中 |
| `delivered` | `delivered` | 已交付 |
| `failed` | `failed` | 已失败/已拒绝（含具体原因） |
| `timeout` | `expired`（看门狗截止强杀） | 以失败呈现，配专用超时文案 |
| `cancelled` | —（V1 取消仅发生在租约之前） | 已取消 |

注意 `expired` 一词只存在于作业层，语义是**截止时间强杀**——对用户永远呈现为一种失败（有自己的文案），绝不写成「已过期，请重新检查」。官方来源的时效由 requirements 快照的年龄管理，与这个词无关。

### 5.2 V1 关键转移

主干：

```text
draft → intake → queued → running → qa_pending → review_pending → delivered
```

分支与异常路径（全部对应 A 章既有转移，无新增状态）：

- **`qa_pending → queued`**：QA 或服务端校验失败、尝试次数未用尽 → 以**全新尝试**重新入队（QA issues 回灌进尝试输入）；尝试耗尽 → `failed`（`qa_failed`）。不存在 `machine_qa → generating_pack` 式的“回跳”：一次生成是一个整体作业，完成由产物出现（`qa-report.json` + delivery/）被动检测，不是可分步操控的子状态。
- **`running → timeout`**：超出墙钟截止（看门狗强制销毁容器）→ 有剩余尝试则重新入队，否则 `failed`。
- **`running / qa_pending → failed`**：不可重试的失败类别或尝试耗尽；写入结构化 `failure_reason`，用户看到具体原因，触发退款/补偿钩子。
- **`review_pending → delivered`**：运营人员批准并放行（见 5.3）。
- **`review_pending → failed`**：运营人员驳回，附结构化、机器可读的原因（见 5.4）。
- **取消（用户自助）**：仅限 `draft / intake / queued`（租约之前）。`queued` 已经付费，其取消规则必须明说：材料包信用退还（原路退款或保留信用，上线前定稿其一）。运行开始后 V1 不支持自助取消——走客服渠道 + 运营操作。intake 长期未完成由收割器处理为 `cancelled`（`user_abandoned`）——这是弃置，绝不称为“过期”。
- **`awaiting_user`（运行中途向用户提问）**：目标架构状态（A 章 §1.7），V1 明确不实现。`researching → 需要用户补充` 一类的中途分支属于 V1 之后、与 `awaiting_user` 一起落地。

`route_not_supported` 不在状态机里：路线支持与否是**创建申请之前**路线查询的结果。不支持 → 写一条轻量等待名单记录，案件根本不会被创建。

### 5.3 delivered 的语义

`delivered` = **运营人员批准 + 材料包放行**（签发交付链接）。用户是否下载、何时下载、下载几次，都以事件记录（`case_events` / 下载日志），绝不驱动状态转移。留存时钟自交付起算（各类数据的留存窗口见架构 B 章 §3）。

### 5.4 补材料在 V1 的机制（不是状态）

V1 运营人员的动词只有两个：**批准 → `delivered`**；**驳回 → `failed` + 结构化原因**（机器可读的原因码 + 说明，经短信与申请页呈现给用户）。用户据此修改 intake / 重新上传，**重新提交 = 入队新一次完整生成尝试**：受 `max_attempts` 约束、材料包信用保留（不再收费）、消耗真实 LLM 成本与约 10 分钟耗时。

UX 上这仍可以长得像一个“补材料”页面，但它的数据支撑是 `failure_reason`，不是一个新状态，也不是一张独立的补材料请求表。带状态的请求/响应闭环（`review_pending → queued` 携带运营反馈、`awaiting_user` 中途追问）是 V2/目标架构路径，在此记录为演进方向，不进入 V1。

### 5.5 状态机设计原则

1. **LLM 不决定最终业务状态**：LLM 可以生成建议、文档和检查结果，但状态转换由后端工作流以带守卫的 SQL 更新执行（架构 A 章不变量）。
2. **人工审核是强制状态**：不能从 `qa_pending` 直接进入 `delivered`。
3. **产品文档不发明状态名**：任何“新状态”的需求都必须先落进架构 A 章的枚举，再回到产品文档。
4. **支付是守卫，不是状态**：`pack_credits` 决定能否入队，状态机对钱不知情。
5. **一次生成是一个整体作业**：完成由产物证据判定，失败重试 = 新尝试；不存在可回跳、可操控的内部子状态。
6. **“过期”一词保留给作业截止强杀**，对用户呈现为失败；申请弃置是取消（`user_abandoned`），来源时效由 requirements 快照年龄管理。
7. **所有交付前状态都应该可追踪**：用户和运营方都能看到申请卡在哪里。

## 6. Visa Master 服务蓝图

前台动作以手机端机制书写（它更陌生、更容易被漏掉）；同一动作的电脑端形态见[移动端平权](../guidelines/mobile-parity-zh.md) §3.11，跨设备切换见 §3.12。两端都属于完成定义，本表只点名。

| 阶段 | 用户前台动作（以手机端机制书写，电脑端形态见 §3.11） | 系统后台动作 | AI/Agent 动作 | 人工动作 | 用户可见输出 |
|---|---|---|---|---|---|
| 了解产品 | 在小红书/微信 webview 内浏览首页、样例 | 记录来源渠道 | 无 | 无 | 价值说明、流程、样例（预渲染页面图片） |
| 判断路线 | 选择城市/国家/签证类型（国籍默认中国公民） | 路线匹配（纯代码规则）；不支持时写入等待名单记录 | 无 | 无 | 支持（主路径）/ 暂不支持 + 等待名单（次要路径） |
| 填写资料 | 完成 intake form（自动保存，中断可续） | 服务端保存草稿；zod schema 校验 + 确定性一致性规则（`packages/core`） | 无（付款前无任何 LLM/OCR 调用） | 无 | 进度、错误与矛盾提示 |
| 上传材料 | 拍照/相册/文件上传，多页页组，断点续传 | 文件存储、分类、权限控制；质量复检回填逐项状态 | 无（OCR 见表下注） | 无 | 逐项状态（只声称真正检查过的：格式/大小/页数/拍摄质量） |
| 支付 | 在系统浏览器完成支付宝支付（微信内经逃生舱 + 鉴权接力） | Stripe webhook 翻转 `pack_credits`（守卫，非状态）；锁定服务范围 | 无 | 无 | 收据、提交确认（支付状态由 webhook 驱动，与跳转回程无关） |
| 官方来源研究 | 可关页离开；进度完全异步 | 入队并租约 `produce_pack` 作业；写 `progress.stage=research` | 浏览官方来源、下载 PDF、记录来源 | 无 | “官方来源核对中” |
| 文档生成 | 同上 | `progress.stage=documents` | 生成表格说明、行程、cover letter、证明模板 | 无 | “材料生成中” |
| 机器 QA | 同上 | 渲染、服务端校验流水线、记录 QA；失败 → 新尝试重新入队或 `failed` | 发现不一致或缺失 | 无 | “一致性检查中” |
| 人工审核 | 等待；状态变化经短信通知（V1，邮件为辅） | 进入 `awaiting_review` 队列，SLA 计时 | 提供 AI 生成摘要 | 批准 → 交付；驳回 → 结构化原因 | “人工复核中”；驳回时列明缺什么、为什么、如何补 |
| 补材料（如被驳回） | 短信深链 → 手机拍摄补件 → 重新提交 | 入队新一次完整生成（`max_attempts` 约束，信用保留） | 新尝试重跑完整流水线 | 复核新结果 | 「重新生成约需 10 分钟」预期文案 |
| 交付 | 浏览器内材料包查看器逐页查看；获取打印合订 PDF；发送链接到邮箱 | 签发短时效签名链接；下载记为事件；留存时钟自交付起算 | 无 | 批准放行（即交付动作本身） | 在线查看器、checklist、打印合订 PDF、邮件链接（zip/逐文件为次要） |
| 后续支持 | 查看 FAQ 或联系支持 | 创建支持 ticket | 可选：初步回答 | 人工处理复杂问题 | 答复、修正、补充说明 |

付款前各行的 AI 列写“无”是刻意的（ADR-002 / [架构 v0.4](../../doc/architecture-v0.4-zh.md)）：intake 一致性检查是 `packages/core` 中的确定性 zod/规则代码。OCR、AI 矛盾提示是 **V1 之后的网关候选任务**——立项时需要自己的 job kind、成本行和 PII 论证，不作为蓝图里的“可选”格子存在。

## 7. 建议的合并产物

实际团队协作时，可以把这四类文档合成一个“申请流程主文档”，结构如下：

```text
1. 用户旅程：用户从想办签证到拿到材料包
2. 核心任务流：用户在产品中怎么操作
3. 状态机：每一步对应什么系统状态（沿用架构 A 章词汇，不另造）
4. 服务蓝图：每个状态背后的 AI、后端、人工动作
5. 页面映射：每个状态对应哪个页面/组件/通知，
   并写明每个状态在两端的行为（webview 内如何呈现、电脑端如何呈现、通知如何触达）
```

这样既不会重复，又能让产品、前端、后端、AI workflow、运营审核使用同一套流程语言。
