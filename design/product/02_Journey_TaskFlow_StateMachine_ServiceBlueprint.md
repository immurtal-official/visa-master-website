# 用户旅程、核心任务流、状态机、服务蓝图：区别与 Visa Master 版本

## 1. 这几个概念为什么看起来重复？

你感觉它们重复是对的，因为它们都在描述“用户如何从需求走到交付”。

但它们的观察角度不同：

| 概念 | 主要视角 | 关注问题 | 产出对象 |
|---|---|---|---|
| 用户旅程图 | 用户体验视角 | 用户每一步想什么、怕什么、看到什么 | 产品、设计、文案 |
| 核心任务流 | 操作路径视角 | 用户完成一个目标需要点击/填写哪些步骤 | 产品、前端、UX |
| 状态机设计 | 系统实现视角 | 系统有哪些状态、什么事件触发状态变化 | 后端、工程、产品 |
| 服务蓝图 | 前后台协作视角 | 用户前台动作如何触发后台 AI、人工审核、通知、交付 | 产品、运营、工程 |

一句话区分：

> 用户旅程图讲“用户怎么感受这件事”；核心任务流讲“用户怎么操作”；状态机讲“系统怎么判断当前进度”；服务蓝图讲“前台和后台如何一起完成服务”。

---

## 2. 对 Visa Master 来说，它们确实应该合并理解

Visa Master 是一个工作流产品，不是普通内容网站。用户不是简单浏览信息，而是经历一个完整服务流程：

1. 选择签证路线。
2. 填写个人和旅行信息。
3. 上传材料。
4. 支付。
5. 系统/AI 处理。
6. 机器 QA。
7. 人工审核。
8. 用户补材料或确认。
9. 下载材料包。
10. 按 checklist 提交。

所以这几个文档会天然相似。合理做法不是强行分开，而是：

- 用 **用户旅程图** 描述体验和心理。
- 用 **核心任务流** 指导页面和交互。
- 用 **状态机** 指导数据库和后端逻辑。
- 用 **服务蓝图** 指导 AI、人工审核和运营流程。

## 3. Visa Master 用户旅程图

### 阶段 1：产生需求

**用户行为**：

- 想去西班牙/欧洲/美国旅游或商务短停。
- 开始搜索“西班牙签证 成都 旅游签 材料”或“美国 B1/B2 签证 怎么办”。
- 比较旅行社、攻略、小红书、官网。

**用户心理**：

- 不确定自己该看哪个官网。
- 担心领区、签证中心、材料要求不同。
- 担心表格填错。

**产品机会**：

- 首页直接解释：按城市、目的地、签证类型生成材料包。
- 强调官方来源和人工复核。

---

### 阶段 2：判断是否适合使用 Visa Master

**用户行为**：

- 进入首页。
- 查看支持路线、价格、交付内容、样例。
- 查看隐私和免责声明。

**用户心理**：

- 这个是不是旅行社？
- AI 会不会乱写？
- 能不能真的生成可用材料？
- 我的隐私安全吗？

**产品机会**：

- 明确说明：不是代替领馆决定，不承诺过签。
- 明确说明：帮助准备材料、减少不一致、引用官方来源、人工复核。
- 展示样例包目录。

---

### 阶段 3：开始申请

**用户行为**：

- 选择申请人国籍。
- 选择所在城市/常住地。
- 选择目的国家。
- 选择签证类型。
- 选择预计出行日期。

**用户心理**：

- 我是不是选对了路线？
- 成都到底归哪里管？
- 我能不能申请这个类型？

**产品机会**：

- 用路线识别器判断是否支持。
- 不支持路线时给出“暂不支持/加入等待名单/人工咨询”选项。

---

### 阶段 4：填写 intake form

**用户行为**：

- 填写个人信息、护照信息、工作信息、收入、储蓄、旅行计划。
- 填写是否独自旅行、是否有同行人、是否有人资助。
- 保存草稿。

**用户心理**：

- 为什么要问这个？
- 我不知道怎么填怎么办？
- 如果填错会不会影响签证？

**产品机会**：

- 每个敏感字段旁边有解释。
- 明确“用于生成材料，不会自动提交给领馆”。
- 关键字段做一致性提示。

---

### 阶段 5：上传材料

**用户行为**：

- 上传护照、银行流水、在职证明或工作信息、户口/身份证等材料。
- 根据 checklist 补充缺失文件。

**用户心理**：

- 上传这些安全吗？
- 哪些必须上传，哪些可以后补？
- 银行流水要几个月？

**产品机会**：

- 材料清单按“必须 / 推荐 / 可选 / 视情况”分组。
- 对每项材料解释用途。
- 给隐私说明和删除说明。

---

### 阶段 6：支付与提交

**用户行为**：

- 确认服务范围。
- 支付。
- 正式提交生成。

**用户心理**：

- 付了钱会得到什么？
- 多久能交付？
- 如果材料不够怎么办？

**产品机会**：

- 付款前明确交付内容。
- 明确“不承诺签证结果，只提供材料准备与一致性检查”。
- 明确预计交付时间和补材料机制。

---

### 阶段 7：AI/系统生成材料包

**用户行为**：

- 等待系统处理。
- 查看进度页面。

**用户心理**：

- 系统现在在做什么？
- 是不是卡住了？
- 生成的东西可靠吗？

**产品机会**：

- 显示进度：官方来源检查、材料解析、文档生成、一致性校验、人工复核。
- 不需要实时展示全部内部细节，但要让用户知道流程在推进。

---

### 阶段 8：人工审核

**用户行为**：

- 等待人工审核。
- 可能收到补充信息请求。

**用户心理**：

- 人工审核是不是认真看？
- 为什么还要补材料？

**产品机会**：

- 把人工审核作为信任机制，而不是延迟。
- 补材料请求要具体：缺什么、为什么缺、如何补。

---

### 阶段 9：交付材料包

**用户行为**：

- 下载材料包。
- 查看 Start Here checklist。
- 按顺序打印、签字、预约或递交。

**用户心理**：

- 这些材料怎么用？
- 哪些要打印？
- 哪些要签字？
- 哪些只是说明？

**产品机会**：

- 文件夹结构清楚。
- 第一个文件必须是 Read-first master checklist。
- 提供提交顺序、打印/签字提醒、来源警示。

## 4. Visa Master 核心任务流

### 主任务流：生成签证材料包

```text
进入首页
→ 选择“开始准备签证材料”
→ 选择申请人国籍
→ 选择当前居住城市/领区
→ 选择目的国家
→ 选择签证类型
→ 系统判断是否支持路线
→ 创建申请草稿
→ 填写 intake form
→ 上传必要材料
→ 系统提示缺失/矛盾信息
→ 用户修正
→ 支付
→ 提交生成
→ AI/系统生成材料包
→ 机器 QA
→ 人工审核
→ 如需补充，用户补材料
→ 审核通过
→ 下载材料包
→ 查看 checklist 并准备递交
```

### 补材料任务流

```text
收到补材料提醒
→ 打开申请详情页
→ 查看缺失项/矛盾项
→ 阅读原因说明
→ 上传新文件或修改字段
→ 重新提交
→ 系统重新检查
→ 回到人工审核
```

### 代他人申请任务流

```text
创建申请
→ 选择“我为他人申请”
→ 填写实际申请人信息
→ 填写联系人/操作者信息
→ 上传申请人材料
→ 系统在所有文档中使用实际申请人信息
→ 联系人与申请人信息分开保存
```

## 5. Visa Master 状态机设计

### 5.1 核心申请状态

| 状态 | 含义 | 用户可见文案 |
|---|---|---|
| `draft` | 已创建申请，但未提交 | 草稿中 |
| `route_not_supported` | 当前路线暂不支持 | 暂不支持该路线 |
| `intake_in_progress` | 用户正在填写资料 | 正在填写资料 |
| `documents_required` | 需要上传材料 | 等待上传材料 |
| `ready_for_payment` | 基本信息完整，可付款 | 可以提交并付款 |
| `paid_pending_submission` | 已付款但尚未正式提交 | 待确认提交 |
| `submitted` | 用户已正式提交 | 已提交 |
| `researching_sources` | 系统查询官方来源 | 正在核对官方要求 |
| `generating_pack` | 正在生成材料 | 正在生成材料包 |
| `machine_qa` | 机器一致性和渲染检查 | 正在进行一致性检查 |
| `human_review` | 人工审核中 | 人工复核中 |
| `needs_user_input` | 需要用户补充或修正 | 需要补充信息 |
| `ready_for_delivery` | 审核完成，可交付 | 材料包已准备好 |
| `delivered` | 用户已下载/交付完成 | 已交付 |
| `cancelled` | 用户或系统取消 | 已取消 |
| `expired` | 长时间未完成或来源过期 | 已过期，请重新检查 |

### 5.2 关键状态转换

```text
draft
→ intake_in_progress
→ documents_required
→ ready_for_payment
→ paid_pending_submission
→ submitted
→ researching_sources
→ generating_pack
→ machine_qa
→ human_review
→ ready_for_delivery
→ delivered
```

异常路径：

```text
human_review
→ needs_user_input
→ human_review
```

```text
researching_sources
→ needs_user_input
```

```text
machine_qa
→ generating_pack
```

```text
any pre-delivery state
→ cancelled
```

```text
draft / intake_in_progress
→ expired
```

### 5.3 状态机设计原则

1. **LLM 不决定最终业务状态**：LLM 可以生成建议、文档和检查结果，但状态转换由后端工作流控制。
2. **人工审核是强制状态**：不能从 `machine_qa` 直接进入 `delivered`。
3. **补材料是正式状态，不是聊天消息**：补材料请求应该结构化存储。
4. **所有交付前状态都应该可追踪**：用户和运营方都能看到申请卡在哪里。
5. **过期状态必须存在**：签证要求、费用、表格可能变化，长时间未完成的申请不能无限复用旧来源。

## 6. Visa Master 服务蓝图

| 阶段 | 用户前台动作 | 系统后台动作 | AI/Agent 动作 | 人工动作 | 用户可见输出 |
|---|---|---|---|---|---|
| 了解产品 | 浏览首页 | 记录来源渠道 | 无 | 无 | 价值说明、流程、样例 |
| 判断路线 | 选择城市/国家/签证类型 | 路线匹配 | 可选：解释路线规则 | 无 | 支持/不支持结果 |
| 填写资料 | 完成 intake form | 保存草稿、校验字段 | 可选：提示矛盾信息 | 无 | 进度、错误提示 |
| 上传材料 | 上传文件 | 文件存储、分类、权限控制 | 可选：OCR/解析 | 无 | 材料 checklist |
| 支付 | 完成付款 | 创建订单、锁定服务范围 | 无 | 无 | 收据、提交确认 |
| 官方来源研究 | 等待处理 | 创建 job | 浏览官方来源、下载 PDF、记录来源 | 无 | “正在核对官方要求” |
| 文档生成 | 等待处理 | 调用文档生成 pipeline | 生成表格说明、行程、cover letter、证明模板 | 无 | “正在生成材料包” |
| 机器 QA | 等待处理 | 渲染、检查、记录 QA | 发现不一致或缺失 | 无 | “正在检查一致性” |
| 人工审核 | 等待或补充材料 | 分配审核任务 | 提供 AI 生成摘要 | 审核材料包、标记问题 | “人工复核中”或“需补充信息” |
| 交付 | 下载材料包 | 生成下载链接、记录交付 | 无 | 可选最终确认 | 文件夹、checklist、来源说明 |
| 后续支持 | 查看 FAQ 或联系支持 | 创建支持 ticket | 可选：初步回答 | 人工处理复杂问题 | 答复、修正、补充说明 |

## 7. 建议的合并产物

实际团队协作时，可以把这四类文档合成一个“申请流程主文档”，结构如下：

```text
1. 用户旅程：用户从想办签证到拿到材料包
2. 核心任务流：用户在产品中怎么操作
3. 状态机：每一步对应什么系统状态
4. 服务蓝图：每个状态背后的 AI、后端、人工动作
5. 页面映射：每个状态对应哪个页面/组件/通知
```

这样既不会重复，又能让产品、前端、后端、AI workflow、运营审核使用同一套流程语言。
