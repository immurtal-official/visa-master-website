# Visa Master MVP 范围：V1 成都→西班牙申根旅游签，V2 相邻路线扩张

## 1. MVP 总原则

Visa Master 的 MVP 不应该追求“覆盖所有国家所有签证”，而应该证明一个更关键的假设：

> 对一个具体签证路线，系统是否能稳定地把用户 intake 信息转化为官方来源可追溯、材料互相一致、经过机器检查和人工复核的可提交材料包。

因此，V1 要极窄，但要完整。

V1 还有一条与"窄而完整"同级的横向约束（2026-08-09 长期指令）：**所有用户端必须项都以移动端网页为第一交付形态，功能与桌面端完全对等。** 发现与完成都发生在手机上（小红书/微信 in-app webview），因此每个必须项的验收标准都必须写明移动端行为——拍照上传、webview 内支付接力、在手机上阅读和使用材料包——不存在"桌面先做完、移动以后再说"的功能。环境约束与逐环节需求见 [移动端平权](../guidelines/mobile-parity-zh.md)，本文档只在各功能处点明要求，不重复其细节。

---

## 2. V1 范围：成都 → 西班牙申根旅游签证

### 2.1 V1 目标

证明以下能力：

1. 用户能在线完成结构化 intake。
2. 系统能基于成都领区和西班牙申根旅游签证生成材料清单。
3. 系统能生成一个完整材料包。
4. 材料包内的信息前后一致。
5. 人工审核可以在可控时间内完成。
6. 用户愿意为这个结果付费。

---

### 2.2 V1 支持对象

| 维度 | V1 范围 |
|---|---|
| 申请人国籍 | 中国公民 |
| 当前地点 | 成都领区相关用户 |
| 目的地 | 西班牙 |
| 签证类型 | 申根旅游签证 |
| 出行目的 | 仅个人旅游。探亲/商务/会议是相邻需求、后续路线：路线查询把它们导向 waitlist 登记，不作为已支持路径 |
| 就业状态 | 仅在职申请人——唯一验证过的模板集是在职形态。学生与退休申请人在路线/intake 入口、付款前明确拦截（最近的模板变体扩展方向，见 2.6） |
| 用户类型 | 本人申请，或简单代他人申请（一位操作人 + 一位申请人，见 2.3 第 3 条） |
| 交付形式 | 浏览器内材料包查看器为主 + 打印合订 PDF + 邮件链接；zip 为次要路径（见 2.3 第 8 条） |
| 审核方式 | 每单人工复核 |

### 2.3 V1 用户端功能

#### 必须有

1. **路线选择**
   - 申请人国籍（默认中国公民，仅例外情况下询问）
   - 当前居住城市/领区
   - 目的国家
   - 签证类型
   - 出行目的（V1 仅个人旅游；探亲/商务/会议选项导向 waitlist 登记，不进入付费流程）
   - 出行时间
   - 就业状态门槛：学生、退休申请人在此处或 intake 入口、**付款之前**明确告知暂不支持，并登记 waitlist

2. **账号与申请草稿**
   - 创建申请
   - 保存进度：草稿在服务端逐步自动保存——在微信 webview 里，被打断才是中位数会话（[移动端平权](../guidelines/mobile-parity-zh.md) §3.3）
   - 回来继续填写：登录后精确恢复到中断位置
   - **对开发计划第 2 周的修订请求**：现计划只在提交时插入 `queued` 作业行；本范围要求第 2 周同时落地草稿持久化——草稿行（或 `status='draft'`）+ 基于共享 zod schema partial 的逐步自动保存 + 登录恢复

3. **Intake form**
   - 个人基本信息
   - 护照信息
   - 工作/收入信息
   - 储蓄/财务信息
   - 旅行计划
   - 同行人/资助情况
   - 历史签证或拒签情况
   - 代他人申请（简单形态：一位操作人 + 一位申请人）：申请人与账号持有人在数据结构上是两个人，字段与文案绝不混用；上传任何被申请人材料之前，采集其明确的第三方授权同意（PIPL 要求）。付款人、联系人等更多角色 V1 不建模，留给 V2+ 随真实功能引入

4. **材料上传**
   - 护照
   - 银行流水或资产证明
   - 在职/收入相关信息
   - 其他根据路线需要的材料
   - 首要上传路径是手机拍照/相册/文件选择，带即时质量把关（模糊/反光/分辨率）与多页页组；上传分块、可断点续传（[移动端平权](../guidelines/mobile-parity-zh.md) §3.4）

5. **支付与提交**
   - 单次材料包付费：对客户只展示**一个价格**（单一 SKU，对应一个 Stripe Payment Link；工作占位 ¥299，上线前最终定价）
   - 微信/小红书 webview 内结账不做跳转，走逃生舱插页 + 鉴权接力到系统浏览器（Stripe + 支付宝）；已支付状态由 webhook 驱动（[移动端平权](../guidelines/mobile-parity-zh.md) §3.5）
   - 明确服务范围
   - 明确不承诺过签

6. **进度页**
   进度页文案是对架构 v0.4 Chapter A 案件状态的**映射**，不发明新状态：
   - `queued` → 已提交，排队等待生成
   - `running`（运行内阶段 research/documents）→ 官方来源核对中 / 材料生成中
   - `qa_pending`（阶段 qa）→ 一致性检查中
   - `review_pending` → 人工复核中
   - `delivered` → 已交付
   - `failed` → 已失败 / 已拒绝（含结构化原因；用户的下一步动作见第 7 条）
   - 看门狗超时强杀（作业层 `expired`）对用户呈现为**失败**并配专用文案，绝不呈现为"已过期请重新检查"
   - 没有独立的"需要补充信息"状态——补材料就是"已拒绝（含原因）"的用户侧动作（第 7 条）

   进度完全异步，不假设用户开着页面等待：**状态变更的出站通知属于 V1 范围，短信为主、邮件为辅**（公众号模板消息是 V2；[移动端平权](../guidelines/mobile-parity-zh.md) §3.6）。

7. **补材料流程**
   **范围决定（使本范围与开发计划对齐）**：V1 的补材料不引入新状态，也不建请求表。运营端动词只有两个——批准 → `delivered`，驳回 → `failed` + 结构化、机器可读的原因，逐项呈现给用户。用户端体验仍可以长得像一个"补材料"页面（列出缺失或矛盾之处、复用同一套拍摄与页组组件），但它由 `failure_reason` 驱动：
   - 用户修改 intake / 补拍上传后**重新提交，入队一次新的尝试**（受 `max_attempts` 约束，材料包购买额度保留）
   - 每次重跑消耗真实 LLM 成本、约需 10 分钟——文案向用户明示"重新生成约需 10 分钟"
   - 带状态的请求/响应闭环（`review_pending` 携带运营反馈重回队列、`awaiting_user` 运行中交互）是 **V2/目标架构路径**，在此记录为后续事项，V1 不实现

8. **交付下载**
   - **浏览器内材料包查看器是首要交付形态**（在微信 webview 内完整可用）：文件树 + 逐文件预渲染页面预览，每个 DOCX 配一份 PDF 转制版
   - 文件目录说明、Read-first checklist、官方来源和 caveats 都渲染为原生页面——只有手机的用户不下载任何文件即可读完 checklist、逐份浏览模板并对照字段指南核对内容；需要编辑模板时，用"把材料包发到我邮箱"的签名链接留待桌面处理，或直接使用打印合订件后手工填写
   - 每包生成一份**打印合订 PDF**（"发给打印店的文件"，按递交顺序合并、标记需签字页）——这是纯手机走完递交准备的关键产物
   - "把材料包发到我邮箱"发送签名**链接**（非附件）；zip 下载为次要路径（经逃生舱进入系统浏览器后）
   - 优先级与链接时效细节见 [移动端平权](../guidelines/mobile-parity-zh.md) §3.8

9. **PII 生命周期**
   - 用户可见的留存策略说明（ToS/隐私页）
   - 强制执行的留存窗口：上传件案件关闭后 90 天、作业中间产物 30 天、已交付材料包 180 天（架构 v0.4 Chapter B §3）
   - beta 阶段的按请求人工清除 runbook（对应开发计划第 7 周）

### 2.4 V1 后台功能

#### 必须有

1. **申请列表**
   - 状态筛选
   - 待审核队列（`awaiting_review`）
   - V1 就是这两样（与开发计划第 4 周对齐）；单路线阶段路线筛选没有意义，推迟到 Phase 2 路线扩张时引入

2. **申请详情**
   - 用户 intake 数据
   - 上传材料
   - AI/Agent 输出
   - QA 报告
   - 来源列表

3. **人工审核 checklist**
   - 材料是否完整
   - 关键字段是否一致
   - 来源是否当前有效
   - 是否需要补材料
   - 是否可交付

4. **驳回与补材料原因**
   - 驳回时填写结构化、机器可读的原因：指定字段/文件 + 说明
   - 原因作为 `failure_reason` 逐项呈现在用户端的补材料页（见 2.3 第 7 条）
   - 不建独立的补材料请求表；带状态的请求/响应闭环是 V2/目标架构路径

5. **交付控制**
   - 人工确认后才允许交付
   - 生成下载链接
   - 记录交付时间

---

### 2.5 V1 交付内容

材料包结构（与真实验证过的材料包在磁盘上的结构一致，编号 00–04 连续）：

```text
00_Start_Here/
  Read-first master checklist
  Submission index

01_Official_Documents/
  官方 checklist
  申请表 PDF 或说明
  相关 acknowledgement/questionnaire

02_Editable_Templates/
  Application form field guide
  Employment & leave certificate
  Day-by-day itinerary
  Cover letter
  Optional financial explanation

03_本人材料待添加/ (03_Your_Documents_To_Add)
  护照与照片
  户口簿
  在职与公司材料
  银行流水
  保险
  交通与住宿预订单

04_Sources_and_Warnings/
  Sources cited
  Current caveats
  Human review notes
```

03 是用户自备材料的占位目录：材料包用它告诉用户"哪些东西要你自己放进去、放在哪"，与 checklist 逐项对应。营销面（如首页预览卡片）展示这套结构时，用中文标签为主、英文目录名作小字辅注，且可以不带编号。

### 2.6 V1 明确不做

| 不做 | 原因 |
|---|---|
| 不承诺签证通过 | 签证结果由领馆决定 |
| 不自动替用户提交 | 涉及预约、签字、现场材料、本人到场等复杂事项 |
| 不覆盖所有申根国家 | 每个目的国和领区规则不同，先验证一个路线 |
| 不做多申请人/家庭成员分开管理 | 会显著增加数据结构和审核复杂度；明确排期为 Phase 4。V1 只有一位操作人 + 一位申请人 |
| 不做跨申请一致性检查 | 情侣/家庭同行时，V1 不在多份申请之间核对日期/路线/酒店的一致性——这是明说的已知局限。廉价缓解（第二份 intake 从既有申请克隆行程级数据）是 Phase 2 候选 |
| 不服务学生/退休申请人 | 唯一验证过的模板集是在职形态；在付款前入口拦截（见 2.2/2.3）。两者是最近的模板变体扩展：学生（在读证明+资助模板）、退休（退休证明+养老金/存款财务叙事） |
| 不服务探亲/商务/会议出行 | V1 仅个人旅游；这三类是相邻需求、后续路线，路线查询导向 waitlist |
| 不留存不必要的数据 | 支付凭据只经 Stripe，永不进入本系统；除 2.3 第 9 条留存窗口内的材料外，不保留任何其他 PII 副本 |
| 不做完全自动交付 | 人工审核是信任机制和风险控制 |
| 不做开放式 AI 聊天顾问 | 容易产生幻觉和责任边界问题 |
| 不处理复杂拒签史/高风险背景 | 需要专业顾问或律师判断 |

### 2.7 V1 成功指标

所有漏斗与成功指标**以移动端优先统计，至少按设备分段**（[移动端平权](../guidelines/mobile-parity-zh.md) §1）：失败的移动端漏斗不允许藏在被桌面拉高的聚合数字里。

#### 产品指标

- 用户完成 intake 的比例。
- 用户从开始到提交的时间。
- 补材料率。
- 材料包一次通过人工审核的比例。
- 人工审核平均耗时。
- 用户是否成功下载并使用材料包。

#### 商业指标

- 访问首页到开始申请转化率。
- 开始申请到付款转化率。
- 单 pack 毛利。
- 每单人工审核时间。
- 用户愿意支付的价格区间。

#### 质量指标

- 材料一致性错误数量。
- 官方来源过期或错误数量。
- 文档渲染问题数量。
- 用户投诉和退款原因。

## 3. V2 范围：相邻路线扩张

### 3.1 V2 目标

V2 不换游戏规则，而是证明 V1 的路线资产可以复利：**下一个申根目的国和/或下一个中国领区**（对应 §6 Phase 2 与 PRODUCT.md §4 的相邻扩张策略）。每条已解决的路线——官方来源研究、表格字段映射、模板集——都沉淀为缓存资产（requirements cache，开发计划第 5 周），V2 就是让这套缓存与模板复用机制第一次接受"第二条路线"的检验。

---

### 3.2 V2 支持对象

| 维度 | V2 范围 |
|---|---|
| 申请人国籍 | 中国公民 |
| 路线 | 在成都→西班牙之外新增：其他申根目的国（同领区），和/或其他中国领区（同目的国）；先选其一验证 |
| 签证类型 | 申根旅游签证 |
| 出行目的 | 仍仅个人旅游 |
| 交付形式 | 与 V1 相同的材料包形态 |
| 审核方式 | 每单人工复核不变 |

---

### 3.3 V2 应验证的能力

1. **路线作为可复用资产**：新增一条路线的边际研究与模板工作量，有多少能从 requirements cache 与既有模板直接复用。
2. **领区差异建模**：同一目的国在不同领区的中心、表格、费用差异能否用同一套结构表达。
3. **运营端路线筛选**（从 V1 推迟）：申请列表增加路线维度。
4. **随真实功能引入的 V1 遗留项**：带状态的补材料请求/响应闭环（见 2.3 第 7 条）、同行申请的行程克隆缓解（见 2.6）等按需启动。

---

### 3.4 V2 明确不做

| 不做 | 原因 |
|---|---|
| 不引入新签证类型或非旅游出行目的 | 探亲/商务/会议仍走 waitlist，见 2.6 |
| 不对外承诺全国（中国境内）覆盖 | 对外的"即将支持"只指向相邻申根/领区扩张，其余进 waitlist |
| 不承诺美国 B1/B2 | 那是 §4 的后续探索，未过 §5.2 门槛前不做功能级设计 |

---

## 4. V3/后续探索：美国 B1/B2

美国 B1/B2 是被记录在案的**后续探索方向，不是承诺**。它与申根材料包逻辑差异很大——重心在 DS-160 在线表格、面签叙事一致性与移民倾向解释，而非固定材料清单——因此需要独立的产品验证。在 §5.2 的门槛满足之前，不做功能级设计；对外任何界面不承诺美国 B1/B2。

先记录在案的核心风险：

- B1/B2 更接近"面签叙事一致性"问题，不只是材料格式问题。
- 用户可能期待"帮我提高过签率"，需要强边界说明。
- DS-160 相关内容必须特别谨慎，不能替用户虚构。

已确定的边界（届时仍然成立）：

| 不做 | 原因 |
|---|---|
| 不替用户编造面签答案 | 高风险且不合规 |
| 不承诺通过 | B1/B2 高度依赖面签和领事判断 |
| 不自动提交 DS-160 | 用户需要确认和签署真实信息 |
| 不处理复杂移民倾向问题 | 可能需要专业法律建议 |
| 不替代律师 | 产品应定位为材料准备和一致性辅助 |

## 5. 扩展判断

### 5.1 什么时候可以做 V2（相邻路线扩张）？

建议满足以下条件再进入 V2：

1. V1 至少完成 20–50 个真实或 beta 用户 pack。
2. V1 人工审核平均耗时可控。
3. V1 用户愿意为交付结果付费。
4. V1 材料一致性错误率明显下降。
5. V1 的 intake、上传、支付、审核、交付流程已经稳定。

### 5.2 什么时候才考虑 V3（美国 B1/B2）？

在 V2 证明"第二条路线的边际成本显著低于第一条"、且相邻扩张的复用假设成立之前，不为 B1/B2 展开 §4 之外的任何设计。

## 6. 产品路线建议

```text
Phase 0: 内部 demo
- 成都 → 西班牙申根旅游签
- 手动邀请 beta 用户
- Founder 人工审核所有 pack

Phase 1: V1 paid beta
- 公开支持一个路线
- 单次收费
- 基础 dashboard
- 人工审核强制

Phase 2: V2 相邻路线扩张
- 其他申根目的国
- 其他中国领区
- 路线缓存和模板复用
- 运营端路线筛选
- 行程克隆：第二份 intake 从既有申请克隆日期/路线/酒店（同行申请一致性的廉价缓解）
```

## 7. MVP 的关键战略选择

最重要的选择是：

> 不要先做“签证百科网站”，先做“一个路线可真实交付的材料包产品”。

原因：

1. 百科内容容易被免费攻略替代。
2. 用户真正愿意付费的是材料准备、检查和交付。
3. 每个路线的官方来源、表格和领区规则都不同，必须用路线作为基本单位积累。
4. 先做窄路线可以控制质量和人工审核成本。
5. 一旦一个路线跑通，后续扩展才有工程和运营复用价值。
