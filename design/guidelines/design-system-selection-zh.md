## 1. 这个决定需要服务什么

Visa Master 不是一个带联系表单的内容网站，而是一个**高信任、多步骤的流程型产品**：用户交出护照扫描件、银行流水和在职信息，最终拿到一份要打印出来递交给领馆的材料包。因此前端由两个界面主导，设计系统必须两者都擅长：

1. **一个官网首页**，需要在十秒内建立可信度。
2. **一个长的、有分支的、可中断续填的 intake 表单** — 产品真正的核心。

这两个界面都从窄屏开始构建、再撑开。一条长期指令（2026-08-09）确立了**移动优先只指构建顺序、两端地位并重**：移动端网页承载 100% 的产品功能且体验与桌面端同级，桌面端同样承载这 100%，并另有自己的原生优势。§7 承载这条指令在设计系统层面的约束；完整表述见 [`mobile-parity-zh.md`](mobile-parity-zh.md)。

产品设计包已经直接写明了视觉目标：*可信、清晰、现代、轻专业、低焦虑、流程化、可解释*。它同样点名了要避免的：黑底霓虹、过度 AI 感的紫色渐变、旅行社式大图轮播、过度政府网站化、过度企业后台化。

最后这份清单比看上去更重要。它排除了整套照搬任何大厂设计系统的可能，因为每一套都会连带把母公司的品牌气质一起带进来。

## 2. 选型标准

| 标准 | 为什么在这里重要 |
|---|---|
| 视觉中立性 | 品牌必须读起来是*我们自己的*可信服务，而不是一个 Google、Shopify 或 IBM 的产品 |
| 表单与校验的深度 | intake 表单就是产品本身；表单原语弱等于直接出局 |
| 开箱即用的可访问性 | 焦点管理、ARIA 和键盘导航事后补代价很高，且涉及合规 |
| 与 Next.js / React 的契合度 | `apps/web` 是 Next.js；server components 与 hydration 行为是实打实的约束 |
| 逃生舱成本 | 我们需要一批没有任何系统现成提供的组件（材料包文件树、一致性校验报告、来源引用面板） |
| 在中国大陆网络下的体积 | 客户在中国大陆；沉重的 CSS-in-JS 运行时是实际成本 |
| 在大陆内嵌浏览器里的存活能力 | 旅程的很大一部分发生在微信（WKWebView / XWeb）和小红书的 in-app 浏览器里，它们的键盘、焦点和 fixed 定位行为与桌面 Chrome 有分歧 |

## 3. 考虑过的候选

本节回答的问题不是"哪套系统排名最高"，而是"到底该不该整套采用任何一套"。答案是不该；下表的结论记录的是每个候选为何过不了这个问题，而不是一份偏好排序。

| 候选 | 结论 | 理由 |
|---|---|---|
| **Radix UI（+ Tailwind）** | **选中** | 无样式、可访问的原语。我们保留完整的视觉控制权，而这正是一个定制的、以信任为导向的品牌所需要的。与 Next.js 生态重合度最高。通常经由 shadcn/ui 使用，组件是被复制进仓库、由我们自己拥有的，而不是以依赖形式外挂 |
| Chakra UI | 次选 | 自带样式、起步快，但它的主张会透出来，从它的默认往外定制比一开始就中立更贵。运行时样式还会增加体积 |
| Material Design | 排除 | 一眼就是 Google。它的密度和动效语言读起来像消费级 app，而不是专业的材料申报服务 |
| Shopify Polaris | 排除 | 很优秀，但它的每一个模式都假设使用者是商家后台。电商基因会渗进词汇里 |
| IBM Carbon / Microsoft Fluent / Atlassian | 排除 | 企业工具气质 — 恰好就是内容策略警告的"过度企业后台化"这一失败模式 |
| Adobe Spectrum / AWS Cloudscape | 排除 | 同上，且对小团队而言社区支持面更窄 |
| GOV.UK Design System | **仅作为模式借用** | 见 §5 |

## 4. 决定

**基于 Radix UI primitives 构建，用 Tailwind 做样式，组件通过 shadcn/ui 引入仓库，而不是当作一个不透明的依赖来消费。**

具体来说：

- **Radix** 提供行为和可访问性：dialog、popover、select、radio group、tooltip、焦点陷阱、键盘语义。
- **Tailwind** 提供视觉层，由一套 design token 驱动，这套 token 编码的正是内容策略里已经商定的颜色方向 — 蓝 / 青蓝 / 深海军蓝为主色，白色与浅蓝灰为背景，绿色表示成功，橙色表示警示，红色表示错误但刻意降低压迫感。
- **shadcn/ui** 是交付方式，不是依赖。组件以我们拥有、可以随意改动的源文件形式落地 — 这一点很关键，因为我们几个核心页面在任何现成组件库里都找不到对应物。

那些没有任何厂商系统会提供、因而必须由我们自己设计的组件包括：材料包文件树预览、一致性校验报告、来源与警示引用面板、带逐项理由说明的材料上传 checklist、补材料请求流程、可断点续传的上传器、带缩略图排序的多页拍照采集循环（这两个是移动端需求；见 §7），以及语言切换器 —— 它很小，但要承载"材料包语言由目的国决定、而非由界面决定"这句说明（[`internationalization-zh.md`](internationalization-zh.md) §6）。每个组件都先按堆叠式、触控优先的列表来设计，再撑开成它的桌面双栏形态 —— 一个组件、两套一等布局，而不是一套布局加一个降级方案。

## 5. 我们从 GOV.UK 拿什么，不拿什么

GOV.UK Design System 是现存最好的公开参考，针对的正是**高风险、由焦虑且一生只做一次的人来填写的表单**。这恰好就是 intake 表单。我们借用它的*模式*，拒绝它的*皮肤*。（USWDS 是它的美国同类，作为同一类素材的次级参考。）

借用：

- **一页只做一件事。** 直接支撑用户画像文档里"像报税软件，而不是普通网页表单"的原则。
- **提问协议** — 用一个句子把问题问出来，解释就放在旁边，而不是塞进 tooltip。
- **错误信息约定** — 顶部一个错误汇总，逐条链接到对应字段，再配上告诉用户该怎么做（而不是哪里错了）的行内提示。
- **进度与可续填** — 让用户知道自己在一个长任务中的位置，并支持"保存后回来继续"。
- **平实语言规则**，用于任何带有后果的内容。

不借用：视觉语言。GOV.UK 的设计目标就是看起来像政府网站，而内容策略明确排除了这一点。拿它的交互研究，不要它的字体排印和黑色横条。

## 6. 既有分析，以及我们推翻的那一处

一份更早的选型评估 — [`design-system-options-zh`](../../discussion/withchatgpt/design-system-options-zh.md) — 得出的是一个三层结论：官网营销页用 Tailwind + shadcn/ui，intake 用轻量的表单友好组件，**登录后 dashboard 和审核/管理后台用 Ant Design**。其中大部分我们予以保留，而它结尾处的那个观察，是迄今为止关于这个决定写得最锋利的一句：

> 风险在于*名牌 design system 偏差* — 以为背后的公司越大就越合适。design system 的选择是任务匹配，不是品牌崇拜。

予以保留的部分：官网不应该穿任何厂商的默认皮肤；intake 流程需要的是低信息密度，而不是企业级密度；Adobe Spectrum 值得学习其克制，但不适合作为我们的视觉基因；政府类设计系统是高风险表单的正确参考。

这份既有评估还带着一个值得点名的结构性矛盾：它把七套系统排了名（第一 Ant Design……第七 Fluent），结论却是"哪套都不整套采用" — 快速浏览排名的读者会带走"用 Ant Design"的印象，而它自己的结论并不支持这个印象。本文档刻意回答的是那个被排名遮住的问题：不是"哪套系统排名最高"，而是"到底该不该采用任何一套"（§3）。

**同样予以拒绝的：intake 环节使用"类 Material 模式"。** 既有评估提议营销页用 shadcn，但 intake 用类 Material 的表单模式。从营销页 → intake → dashboard 有且只有一套视觉系统，因为访客从营销页跨进 intake 表单的那一刻正是转化的关键信任时刻 — 在这个接缝处出现肉眼可见的视觉语言切换，读起来就像被移交给了另一家公司，而此刻用户恰恰在决定要不要把护照号敲进去。"Material 对移动端友好"也不构成采用 Material 的论据：响应式、触控优先的行为来自我们自己的 Tailwind 层（§7），不需要引入 Google 的品牌语言。

**予以推翻的：管理与审核后台使用 Ant Design。** 支持它的理由是成立的 — Table、Steps、Upload、Drawer、Descriptions、Timeline、Tag 恰好就是审核后台的词汇表，而内部工具没有需要保护的品牌要求。孤立地看，它确实会更快。但开发计划把这个问题判给了反方：`apps/web` 同时承载 Next.js 前端**和审核操作**，而 monorepo 的构成是 `apps/web`、`apps/conductor`、`packages/*`、`infra/` — 并不存在独立的 `apps/admin`。所以 Ant Design 不会是"第二个应用里的第二套设计系统"，而会是**与面向客户的页面处在同一个 bundle 里**的第二套设计系统、第二套 token、第二套组件词汇 — 并被发给那些永远看不到后台页面的中国大陆客户。

只有当审核后台被拆成独立应用时，这笔交易才划算。它日后很可能值得被拆出去 — 审核工具面向不同的使用者、有不同的发布节奏、也有不同的安全姿态。**如果 `apps/admin` 被拆分出来，请重新审视这个决定；** 届时 Ant Design 就是那个应用的首选候选。在那之前，审核后台使用同一套 Radix primitives 构建，接受我们需要自己手写一个数据表格的代价。

## 7. 移动优先只指构建顺序，两端地位并重

一条长期指令（2026-08-09）统辖本节的一切：**移动端网页支持 100% 的产品功能，体验与桌面端同级** — 包括 intake、拍照采集材料、支付、进度、补材料闭环和材料包交付 — **桌面端同样承载这 100%，并另有自己的原生优势。** 任何一端都不是另一端的预告片；旅程可以在任意时点跨设备切换，而跨设备连续性是被设计出来的流程，不是绕行手段。我们从窄屏开始构建，是因为撑开是安全的、收窄不是 —— 这是关于顺序的判断，不是关于哪类客户更重要。

关于交付环境的两个事实驱动了下面的规则。第一，客户抵达时所在的 in-app 浏览器 — 安卓上微信的 XWeb、iOS 上的 WKWebView、小红书的 webview — 是现代引擎，file input 和相机采集原生可用，但文件下载和支付宝跳转被封锁、会话无法带进系统浏览器、也不存在任何推送通道。第二，用户切去聊天时微信会例行杀掉并重载 webview，所以客户端状态只能是缓存，永远不能是记录本身。旅程层面的后果 — 带鉴权接力的逃生舱引导层、短信通知、服务端草稿、断点续传上传、浏览器内材料包查看器、打印合订 PDF — 在 [`mobile-parity-zh.md`](mobile-parity-zh.md) 里逐阶段规定。

约束设计系统本身的规则：

- **浮层。** 移动端上 dialog 变成底部抽屉（shadcn 的 Drawer / Vaul）；键盘弹出时居中的 modal 是 WKWebView 的已知失败模式。
- **下拉选择。** Radix Select 不发给触控设备 — 短列表用带样式的原生 `<select>`，长列表（城市、国籍）用底部抽屉选择器。桌面端可以保留 Radix Select。
- **不依赖 hover 的信息展开。** Tooltip 和 HoverCard 在 intake 和交付流程中全面禁用；解释就放在问题正下方的行内 — 这正是 §5 已采纳的 GOV.UK 协议，移动端只是把它从风格偏好变成了硬性要求。
- **触控目标**最小 44×44pt，相邻可点行之间留 8px 间隔，以 Tailwind token 编码，不留给逐屏判断。
- **输入框**字号最小 16px（消除 iOS 聚焦自动缩放），且每个字段的 `inputmode` / `autocomplete` / `autocapitalize` 属于其绑定 `packages/core` zod schema 的类型定义 — 键盘行为由 schema 驱动，不是逐屏各写各的。
- **视口处理是 token 级的：** 用 `dvh` 而不是 `vh`，用封装 `env(safe-area-inset-*)` 的 safe-area 工具类，并由一个共享的吸底操作栏组件独占 `visualViewport` 键盘重定位逻辑，任何单屏都不得自行重新实现。
- **一套字号体系，按文字系统区分字体栈。** CJK 用系统字体栈渲染（苹方优先），拉丁文用小体积子集化 webfont。在大陆网络上永远不加载中文 webfont。字号体系要在**两种**文字下分别设计和审阅，行高按文字系统设定 —— CJK 需要约 1.7–1.8，拉丁约 1.5（[`internationalization-zh.md`](internationalization-zh.md) §4）。
- **每个组件都要扛得住 +100% 的文字膨胀。** 界面以中文和英文交付，而中文是它将来会承载的语言里最紧凑的一种。任何含文字的元素都不设固定宽度，操作按钮文案不允许截断，也不允许用片段拼字符串。只在中文长度下成立的组件就是没做完（[`internationalization-zh.md`](internationalization-zh.md) §5）。
- **文档预览用服务端预渲染的页面图片**，复用管线里已有的 QA 渲染步骤 — 移动端不上 pdf.js，DOCX 预览也因此与 PDF 预览统一。
- **桌面端布局是被规定出来的，不是继承来的。** 每个自研组件的宽屏变体是它自己的设计、有自己的交互能力 —— 双栏比对、一屏看全材料包树、多文件拖拽、intake 的完整键盘走位（[`mobile-parity-zh.md`](mobile-parity-zh.md) §3.11）—— 由同一套 token 和同一份 schema 构建。一个桌面状态只是"移动端堆叠居中、两侧留白"的组件，是没做完。
- **完成定义：** 每个基础组件在发布前必须在微信 iOS（WKWebView）、微信安卓（XWeb）**以及桌面宽度下**验证通过 — 焦点管理、键盘交互和 fixed 定位恰好是 Radix primitives 负责的部分，也恰好是这些 webview 与桌面 Chrome 分歧最大的地方；而指针与键盘交互能力则是桌面变体证明自身价值的地方。每次发布按 [`mobile-parity-zh.md`](mobile-parity-zh.md) 中的完整设备矩阵做冒烟测试。

## 8. 后果

**接受的代价。** 从无样式原语起步，前期工作量比直接采用带样式的套件更大 — 在第一个页面看起来完整之前，我们要先建好 token 体系和基础组件，而每个浮层和输入组件的移动端变体（§7）属于这套基础建设的一部分，不是日后的适配。这是一个刻意的取舍：intake 表单是长期存在的，在几十个页面上跟别人的主张较劲，比一开始多花的搭建成本更贵。

**任何组件都不得复刻校验规则，也不得硬编码错误文案。** 表单组件的规则来自 `packages/core` 里共享的 zod schema，遵循 [`../README.md`](../README.md) 里定下的基本规矩；一个自带"什么是合法护照号"副本的组件是缺陷，不是便利。而这些 schema 输出的是**消息 key 加参数**而不是句子，由组件按当前语言解析（[`internationalization-zh.md`](internationalization-zh.md) §3）。这是整套 i18n 架构里唯一一件事后补救代价极高的事。

**何时重新审视：** 当我们加入第二个路线族（无论下一条上线的是哪条路线）并发现 intake 表单需要真正不同的分支逻辑时，或者当有设计伙伴加入、且其工作方式是在 Figma 中基于某个特定套件时。
