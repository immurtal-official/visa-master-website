# 设计系统选型

**状态：** V1 已决定

## 1. 这个决定需要服务什么

Visa Master 不是一个带联系表单的内容网站，而是一个**高信任、多步骤的流程型产品**：用户交出护照扫描件、银行流水和在职信息，最终拿到一份要打印出来递交给领馆的材料包。因此前端由两个界面主导，设计系统必须两者都擅长：

1. **一个官网首页**，需要在十秒内建立可信度。
2. **一个长的、有分支的、可中断续填的 intake 表单** — 产品真正的核心。

产品设计包已经直接写明了视觉目标：*可信、清晰、现代、轻专业、低焦虑、流程化、可解释*。它同样点名了要避免的：黑底霓虹、过度 AI 感的紫色渐变、旅行社式大图轮播、过度政府网站化、过度企业后台化。

最后这份清单比看上去更重要。它排除了整套照搬任何大厂设计系统的可能，因为每一套都会连带把母公司的品牌气质一起带进来。

## 2. 选型标准

| 标准 | 为什么在这里重要 |
|---|---|
| 视觉中立性 | 品牌必须读起来是*我们自己的*可信服务，而不是一个 Google、Shopify 或 IBM 的产品 |
| 表单与校验的深度 | intake 表单就是产品本身；表单原语弱等于直接出局 |
| 开箱即用的可访问性 | 焦点管理、ARIA 和键盘导航事后补代价很高，且涉及合规 |
| 与 Next.js / React 的契合度 | `apps/web` 是 Next.js；server components 与 hydration 行为是实打实的约束 |
| 逃生舱成本 | 我们需要一批没有任何系统现成提供的组件（材料包文件树、一致性校验报告、来源引用面板） |
| 在中国大陆网络下的体积 | 客户在中国大陆；沉重的 CSS-in-JS 运行时是实际成本 |

## 3. 考虑过的候选

| 候选 | 结论 | 理由 |
|---|---|---|
| **Radix UI（+ Tailwind）** | **选中** | 无样式、可访问的原语。我们保留完整的视觉控制权，而这正是一个定制的、以信任为导向的品牌所需要的。与 Next.js 生态重合度最高。通常经由 shadcn/ui 使用，组件是被复制进仓库、由我们自己拥有的，而不是以依赖形式外挂 |
| Chakra UI | 次选 | 自带样式、起步快，但它的主张会透出来，从它的默认往外定制比一开始就中立更贵。运行时样式还会增加体积 |
| Material Design | 排除 | 一眼就是 Google。它的密度和动效语言读起来像消费级 app，而不是专业的材料申报服务 |
| Shopify Polaris | 排除 | 很优秀，但它的每一个模式都假设使用者是商家后台。电商基因会渗进词汇里 |
| IBM Carbon / Microsoft Fluent / Atlassian | 排除 | 企业工具气质 — 恰好就是内容策略警告的"过度企业后台化"这一失败模式 |
| Adobe Spectrum / AWS Cloudscape | 排除 | 同上，且对小团队而言社区支持面更窄 |
| GOV.UK Design System | **仅作为模式借用** | 见 §5 |

## 4. 决定

**基于 Radix UI primitives 构建，用 Tailwind 做样式，组件通过 shadcn/ui 引入仓库，而不是当作一个不透明的依赖来消费。**

具体来说：

- **Radix** 提供行为和可访问性：dialog、popover、select、radio group、tooltip、焦点陷阱、键盘语义。
- **Tailwind** 提供视觉层，由一套 design token 驱动，这套 token 编码的正是内容策略里已经商定的颜色方向 — 蓝 / 青蓝 / 深海军蓝为主色，白色与浅蓝灰为背景，绿色表示成功，橙色表示警示，红色表示错误但刻意降低压迫感。
- **shadcn/ui** 是交付方式，不是依赖。组件以我们拥有、可以随意改动的源文件形式落地 — 这一点很关键，因为我们几个核心页面在任何现成组件库里都找不到对应物。

那些没有任何厂商系统会提供、因而必须由我们自己设计的组件包括：材料包文件树预览、一致性校验报告、来源与警示引用面板、带逐项理由说明的材料上传 checklist，以及补材料请求流程。

## 5. 我们从 GOV.UK 拿什么，不拿什么

GOV.UK Design System 是现存最好的公开参考，针对的正是**高风险、由焦虑且一生只做一次的人来填写的表单**。这恰好就是 intake 表单。我们借用它的*模式*，拒绝它的*皮肤*。

借用：

- **一页只做一件事。** 直接支撑用户画像文档里"像报税软件，而不是普通网页表单"的原则。
- **提问协议** — 用一个句子把问题问出来，解释就放在旁边，而不是塞进 tooltip。
- **错误信息约定** — 顶部一个错误汇总，逐条链接到对应字段，再配上告诉用户该怎么做（而不是哪里错了）的行内提示。
- **进度与可续填** — 让用户知道自己在一个长任务中的位置，并支持"保存后回来继续"。
- **平实语言规则**，用于任何带有后果的内容。

不借用：视觉语言。GOV.UK 的设计目标就是看起来像政府网站，而内容策略明确排除了这一点。拿它的交互研究，不要它的字体排印和黑色横条。

## 6. 既有分析，以及我们推翻的那一处

一份更早的选型评估 — [`design-system-options-zh`](../../discussion/withchatgpt/design-system-options-zh.md) — 得出的是一个三层结论：官网营销页用 Tailwind + shadcn/ui，intake 用轻量的表单友好组件，**登录后 dashboard 和审核/管理后台用 Ant Design**。其中大部分我们予以保留，而它结尾处的那个观察，是迄今为止关于这个决定写得最锋利的一句：

> 风险在于*名牌 design system 偏差* — 以为背后的公司越大就越合适。design system 的选择是任务匹配，不是品牌崇拜。

予以保留的部分：官网不应该穿任何厂商的默认皮肤；intake 流程需要的是低信息密度，而不是企业级密度；Adobe Spectrum 值得学习其克制，但不适合作为我们的视觉基因；政府类设计系统是高风险表单的正确参考。

**予以推翻的部分：管理与审核后台使用 Ant Design。** 支持它的理由是成立的 — Table、Steps、Upload、Drawer、Descriptions、Timeline、Tag 恰好就是审核后台的词汇表，而内部工具没有需要保护的品牌要求。孤立地看，它确实会更快。但开发计划把这个问题判给了反方：`apps/web` 同时承载 Next.js 前端**和审核操作**，而 monorepo 的构成是 `apps/web`、`apps/conductor`、`packages/*`、`infra/` — 并不存在独立的 `apps/admin`。

所以 Ant Design 不会是"第二个应用里的第二套设计系统"，而会是**与面向客户的页面处在同一个 bundle 里**的第二套设计系统、第二套 token、第二套组件词汇 — 并被发给那些永远看不到后台页面的中国大陆客户。

只有当审核后台被拆成独立应用时，这笔交易才划算。它日后很可能值得被拆出去 — 审核工具面向不同的使用者、有不同的发布节奏、也有不同的安全姿态。**如果 `apps/admin` 被拆分出来，请重新审视这个决定；** 届时 Ant Design 就是那个应用的首选候选。在那之前，审核后台使用同一套 Radix primitives 构建，接受我们需要自己手写一个数据表格的代价。

## 7. 后果

**接受的代价。** 从无样式原语起步，前期工作量比直接采用带样式的套件更大 — 在第一个页面看起来完整之前，我们要先建好 token 体系和基础组件。这是一个刻意的取舍：intake 表单是长期存在的，在几十个页面上跟别人的主张较劲，比一开始多花的搭建成本更贵。

**移动优先不是可选项。** 产品设计包几乎没有讨论移动端，这是它最大的缺口。这批客户的发现路径压倒性地发生在手机上（小红书、微信搜索），所以首页和路线查询必须按移动优先来设计。把材料上传引导到电脑端完成是可以接受的；手机上第一屏垮掉则不可接受。

**任何组件都不得复刻一份校验规则。** 无论采用哪套设计系统，表单组件的规则都来自 `packages/core` 里共享的 zod schema，遵循 [`../README.md`](../README.md) 里定下的基本规矩。一个自带"什么是合法护照号"副本的组件是缺陷，不是便利。

**何时重新审视：** 当我们加入第二个路线族（V2，美国 B1/B2）并发现 intake 表单需要真正不同的分支逻辑时，或者当有设计伙伴加入、且其工作方式是在 Figma 中基于某个特定套件时。
