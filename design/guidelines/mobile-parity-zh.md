# 移动端平权

**状态：** 长期指令，2026-08-09 决定 — 优先于任何假设单一设备的旧文档
**指令内容：** **移动优先只指构建顺序；两端地位并重。** 移动端网页支持 **100% 的产品功能，体验与桌面端同级** — 发现、路线查询、账号、完整 intake、材料拍照与上传、支付、进度、补材料闭环、材料包交付，全部能在手机上完成。桌面端同样承载这 100%，并另有自己的原生优势（§3.11）。任何一端都不是另一端的降级版本，旅程可以在任意时点跨设备切换（§3.12）。
**配套文档：** [`design-system-selection-zh.md`](design-system-selection-zh.md) §7 — 本文档需求所蕴含的组件级规则
**使用方：** `apps/web`；发布流程（§4）

## 1. 两个设备，地位并重，一个构建顺序

多数客户是在手机上的小红书和微信里找到这个产品的 — 发现端以手机为主，因为获客渠道本身就在手机上。但**发现设备并不决定完成设备**。四种组合都是真实存在且都受支持的：全程手机、全程电脑、手机发现电脑完成、电脑上开始再用手机拍材料。**没有哪一端是"真正的那一端"。**

那为什么构建顺序仍然从移动端开始：响应式设计是不对称的。窄屏 → 宽屏是**做加法**（加列、加密度、一屏显示更多），叠加起来是安全的；宽屏 → 窄屏是**做减法** — 砍导航、折列、藏内容 — 而这正是响应式布局塌掉的地方。所以我们先设计窄的那一版再把它撑开。这是关于**顺序和风险**的判断，**不是**关于哪类客户更重要。

它要防的失败同样是不对称的：一个假设桌面的环节（没有拍照采集的上传、只给 zip 的交付、在微信里死掉的支付跳转）会在所有聚合指标看起来仍然正常的同时，悄悄截断最大入口人群的旅程。

三个实际后果约束下面的一切：

- **验收标准写明两端行为。** 功能不存在"桌面先做完、移动以后再说"，也不存在"移动做完、桌面自然就有了"；两条路径都属于完成定义。
- **任何功能都不为某一端独有。** 每项能力两端都能达成；§3.11 讲的是桌面端做得**更好**的事，而不是**只有**桌面能做的事。
- **漏斗指标按设备分别统计，两端都报。** intake 完成率、从开始到提交的时长、转化率都按设备拆分，任何一端都不是头条数字，任何一端的失败都无法藏在混合后的聚合值里。

## 2. 我们实际交付进去的移动端环境

以下约束是中国大陆移动 web 的事实，不是选择。把它们单列在这里，是因为它们既陌生又致命；相比之下桌面端的环境是常规的，这也是 §3.1–§3.10 读起来偏移动端的原因。这种不对称关乎**陌生程度**，不关乎重要性。§3.1–§3.10 里的每条需求都能追溯到其中一条。

| # | 约束 | 后果 |
|---|---|---|
| E1 | 微信的 webview 在安卓上是 **XWeb**、iOS 上是 **WKWebView**；小红书自带 webview。都是现代引擎（File API、canvas、`visualViewport`、`dvh`），但没有一个能用桌面 devtools 模拟近似 | 在真实矩阵上测试（§4） |
| E2 | 带相机采集的 `<input type="file">` 在所有目标 webview 里**原生可用**；采集不需要微信 JS-SDK，用它反而更差（9 图上限、强制压缩） | 拍照采集是一等路径，无 SDK 依赖 |
| E3 | 微信 webview 里**任意文件下载是死路** — 没有下载管理器，zip 链接走不通，`Content-Disposition: attachment` 在 iOS 上白屏。唯一例外：直接导航到单个 PDF/DOCX 会打开微信内置文档预览器，可"用其他应用打开" | 交付不能依赖下载（§3.8） |
| E4 | 大陆通行的封锁缓解手段是**指向 ··· 菜单的全屏引导层**（"在浏览器打开" / "在Safari中打开"），外加带外链接。用户认识这个套路 | 把这个引导层做成共享组件 |
| E5 | localStorage/cookies 日常可存续，但会**被微信清缓存抹掉、随 webview 驱逐丢失**；用户切去聊天再切回来时，webview 进程会被例行杀掉 | 客户端存储只是缓存；服务端才是记录（§3.2） |
| E6 | **会话不跨上下文**：webview 里设置的 cookie 对系统浏览器不可见，反之亦然 | 每个逃生舱都携带鉴权接力 token（§3.2） |
| E7 | **微信 webview 内的支付：** 只有微信支付 JSAPI 可用，而它需要中国实体、认证服务号、微信支付商户号和 OAuth 拿 openid — V1 一样都没有。支付宝的 app scheme 跳转在微信内**被封锁**，所以 Stripe 的支付宝流程在里面会失败 | webview 内结账 = 逃生舱，永远不是跳转（§3.5） |
| E8 | **微信之外**，经 Stripe 的支付宝 H5 可用，但跳 app 再跳回来的那一程不可靠 | 支付状态由 webhook 驱动，永远不由跳转驱动（§3.5） |
| E9 | **webview 内不存在推送通道**（WKWebView-in-WeChat 和 XWeb 都不支持 web push） | 异步通知 V1 用短信/邮件；公众号模板消息是 V2（§3.6） |
| E10 | **小红书自然流量笔记不能带可点击外链**；只有广告和品牌号可以。小红书 webview 封锁下载和大多数 app scheme 跳转 | 获客按"搜索并手动输入"入口设计（§3.1） |
| E11 | iOS 的 file input 可能给出 **HEIC**；accept 列表排除它时 iOS 通常会转码，但并非总是 | 服务端 HEIC 处理保持强制（§3.4） |
| E12 | **域名可达性是活的约束**：`*.vercel.app` 间歇性被封；未备案的海外域名加载慢，且更容易被微信链接安全系统标记，可能被加插页警告或直接封禁 | 自有域名、大陆侧监控、备用域名（§3.10） |
| E13 | 没有认证公众号（需要中国实体）时，分享进微信的链接只渲染为**裸 URL 卡片** — 没有自定义分享标题/缩略图 | 公众号存在之前链接传播力有限；做好规划，但不依赖它 |

## 3. 按旅程阶段的需求

§3.1–§3.10 规定移动端路径（陌生的那条）。§3.11 规定桌面端必须原生具备、而不是继承而来的能力，§3.12 规定旅程中途在两端之间切换。

### 3.1 进入与发现

- 每个页面检测自己所处的容器（微信的 MicroMessenger UA、小红书的 XHS UA，外加特性检测），并渲染与上下文匹配的交互：微信内下载按钮变成逃生舱引导，支付 CTA 走接力插页，普通浏览器获得完整功能。
- 零承诺漏斗 — 首页、路线查询、如何运作、样例材料包、价格、FAQ — 在微信和小红书 webview 内**100% 可用**：建立信任不需要任何下载、支付或外部跳转。样例材料包以预渲染页面图片浏览，不是文件。
- 因为小红书自然笔记不能外链（E10），获客按**搜索并手动输入**设计：短而好记的域名、经得起小红书搜索的品牌名、URL 被手动输入或粘贴时依然正常的落地页。

### 3.2 鉴权与会话

- 主身份是**大陆手机号 + 短信验证码**（邮箱为辅）。登录在 webview 内 30 秒内完成；验证码输入框用 `inputmode="numeric"` 加 `autocomplete="one-time-code"`。需要尽早排期的运营依赖：可靠的 +86 短信触达需要大陆短信服务商，而后者需要中国实体。
- **每个逃生舱都签发一次性、短时效的接力 token**（URL 或 6 位数字码），把用户直接签入系统浏览器，并落在离开时的那个页面 — 结账、交付页或某个具体文件（E6）。
- **所有草稿和申请状态在每次变更时持久化到服务端**；localStorage 只是写穿式的延迟缓存（E5）。任何流程都能通过登录从冷启动完整重入。

### 3.3 手机上的 intake

- intake 分解为**一页一问的屏幕**（每屏 1–3 个字段，不滚动就能碰到 CTA），配一个 GOV.UK 式的**任务清单枢纽页**，显示各节完成度并支持任意跳入；进度同时显示步骤位置和总百分比。桌面布局是它的适配，不是反过来。
- **输入体工学由字段类型驱动**（绑定 `packages/core` 的 zod schema）：护照号用 `autocapitalize=characters`、`autocorrect=off`、字母数字校验；日期用三个数字输入框，永远不用原生日期滚轮（对久远日期是折磨）；电话用 `inputmode=tel`；金额用 `inputmode=decimal`；拼音字段自动大写；中文姓名字段绝不干扰输入法。所有掩码容忍带空格的粘贴。
- **自动保存**在失焦、步骤切换和 5 秒输入防抖时触发，带可见的已保存指示；重新打开时精确恢复到最后一个未完成的问题。在微信里，被打断才是中位数会话（E5）— 这是表单能填完与被放弃的分水岭。
- **键盘处理：** 吸底 CTA 通过 `visualViewport` 重定位；聚焦的输入框滚动到键盘上方；输入框 ≥16px；WKWebView 里任何 fixed 元素不得困住或压住键盘。
- 每个问题的解释**就放在它正下方的行内**；不确定的字段提供明确的"我不确定"选项；全流程没有 tooltip、没有依赖 hover 的信息展开。

### 3.4 材料拍照与上传

- **手机拍照是首要材料路径** — 普通的 `<input type="file">`，accept 覆盖 `image/*`、HEIC 和 PDF，不强制 `capture=environment`，让系统选择器同时给出相机、相册和文件（E2）。银行流水常常已经以截图或导出文件的形式存在手机里；相册和文件入口与相机同等重要。
- **逐类材料的拍摄引导：** 护照取景框引导，带 MRZ 可见与反光警告；流水引导展示盖章与整页要求。
- **上传前的客户端质量把关** — 模糊检测、亮度与反光启发式、最低分辨率 — 立即给出点名具体问题的重拍提示。审核时隔几天才发现的废片要付出一整个来回的代价；重拍提示只要三秒。服务端复检结果喂给上传 checklist 的逐项状态，而该状态只声称真正检查过的东西。
- **多页材料建模为有序页组：** 逐页拍摄循环，带缩略图、排序、逐页删除与重拍、页数计数器，以及页数偏少提示（6 个月流水很少只有 2 页）。页面在服务端合并为一份逻辑文档。
- **格式与体积：** 接受 HEIC/JPEG/PNG/PDF；客户端缩放压缩到每页约 1–2MB（长边约 2600px，保住 MRZ 可读性）；服务端 HEIC 转码兜底（E11）。
- **所有上传分块且可断点续传**（tus 对接 Supabase Storage 的 resumable 端点或等价物），带重试、退避、逐文件进度，会话经得起页面重载和 webview 进程死亡。材料**只在服务端确认后才算上传成功**，步骤完成以此为门。一次悄悄弄丢护照扫描件、界面却声称成功的整体式 POST，是信任型产品里最糟糕的失败。

### 3.5 支付

- **微信/小红书 webview 内，结账永远不尝试跳转**（E7）。它渲染带接力 token 的品牌化逃生舱插页（E4），让系统浏览器直接落在已鉴权的、带支付宝的 Stripe 结账页上。
- **微信之外，** 结账用 Stripe 加支付宝 H5，但把返回一程当作不可靠（E8）：支付确认**由 webhook 驱动**，每个申请页面 — 包括之后在微信里重新打开的 — 都会重新拉取状态，无论跳 app 再跳回的过程如何收场，已支付状态都会出现。
- 结账文案明确写出 V1 的支付方式是**支付宝、在系统浏览器中完成**。微信支付 JSAPI 是被记录在案的 V2 事项，以中国实体、认证服务号和商户号为前提；移动端不做基于二维码的折衷流程。

### 3.6 进度与通知

- 约 10 分钟的生成和以小时计的人工审核在移动端**完全异步**：进度页任何时刻关掉都安全，状态存在服务端，任何链接重入（包括从微信聊天消息点进来）都深链到当前状态，必要时带鉴权接力。
- **状态变更通知 V1 经短信发出**（邮件为辅；公众号存在后加模板消息）。没有出站通道，审核完成和补材料请求会几天无人看见（E9）。

### 3.7 补材料闭环

- 这个闭环**完全移动原生**：通知 → 深链（带鉴权接力）→ 逐项列出缺失或矛盾之处及审核者理由的页面 → 同一套拍摄与页组组件 → 重新提交。**任何一步都不得要求桌面。** 被要求补的东西 — 一张更清楚的护照照片、再多一页流水 — 恰恰是手机相机几秒钟就能产出的；把这一步推给桌面，等于把 2 分钟的修复变成第二天晚上的任务。

### 3.8 材料包交付

- 交付页**在微信 webview 内以浏览器内材料包查看器的形态完整可用**：一棵文件树，每个文件都能经预渲染页面图片浏览（复用管线的 QA 渲染），每个 DOCX 配一份 PDF 转制版，read-first checklist、打印/签字/递交提醒、来源与警示都渲染为原生页面 — 阅读材料包完全不需要下载（E3）。
- **下载路径按优先级：** (1) "把材料包发到我邮箱"发送签名**链接**（不是附件），供日后在桌面使用；(2) 经逃生舱进入系统浏览器后的逐文件签名 URL 下载（iOS 文件 app 原生解压 zip；在手机上逐文件比 zip 更重要）；(3) 微信内下载按钮替换为引导加邮件选项。微信的单文件预览器对单个文件可接受，对整包永远不行。
- **每包生成一份合并的打印合订 PDF：** 所有可打印页面按递交顺序合并，需签字页在索引中标记，按 A4 排版，在交付页上呈现为"发给打印店的文件"。大陆的打印现实是把一个文件微信发给打印店 — 转发一份合并 PDF 是两下点击的事，转发九个混杂的 DOCX/PDF 不是。这个产物是"纯手机走完全程"得以成立的关键。
- **所有交付链接都是短时效签名 URL**，过期后重新鉴权并再生成而不是 404；邮件里的链接要求登录或接力 token。链接会被转发进微信聊天（配偶、打印店）；一条永久有效、指向全 PII 材料包的 URL 是一起等着发生的 PIPL 事故。交付产物遵循与上传件相同的留存与按请求删除计划。

### 3.9 运营与审核界面

- 刻意声明的有界平权：面向客户的产品是 100%；内部审核工具（一个使用者）欠的是**响应性，不是像素级平权**。三件事必须能在手机上做：带状态和 SLA 计时的审核队列；阅读某份申请（含材料包预览图片）；创建并发送补材料请求。深度审核工作（并排比对、读 QA 报告）保持桌面优先；批准放行可在移动端经同一套预览完成，但不为其优化。移动端上队列渲染为卡片，比把手写的表格做成响应式更便宜。

### 3.10 性能与可达性

- **永远用自有域名**（绝不用 `*.vercel.app`），所有资源自托管，零被封或不稳定的第三方源（不用 Google Fonts/gstatic，不用 unpkg/jsdelivr）。防火墙之后，一个被封的字体源就能把首次渲染挂起 10 秒以上。
- **中文用系统字体栈渲染**（苹方 / HarmonyOS Sans / MiSans / 思源黑体）；永远不加载中文 webfont（好几 MB，直接出局）；唯一例外是小体积子集化的拉丁字体。界面以中文和英文交付，因此两种文字都在这个预算之内 —— 见 [`internationalization-zh.md`](internationalization-zh.md) §4。
- **intake 路由的 JS 预算约 250KB gzip**；营销页静态渲染。用真机在大陆运营商网络下实测 TTFB/LCP；评估中国可达的 CDN 层；一有中国实体就规划 ICP 备案（E12）。
- **主动经营微信域名信誉：** 绝不触发链接刷屏模式，监控插页警告状态，并持有一个预先配置好、迁移路径演练过的备用域名 — 对一个漏斗和交付都跑在微信链接上的产品，域名被封就是全面停摆。

### 3.11 桌面端原生具备的能力

桌面端不是把移动端布局拉宽。下列能力是为大屏和指针设备设计的，也正是客户可能主动选择用电脑完成某一段旅程的原因。它们没有一项是桌面**独有**的 — 每一项在 §3.1–§3.10 里都有可用的移动端路径 — 但在桌面端它们是首要交互方式：

- **多文件拖拽上传。** 把十二页流水一次拖进上传区，沿用与移动端拍摄循环相同的页组模型、排序方式和"服务端确认才算完成"的规则。
- **扫描仪路径。** 平板式或馈纸式扫描往往是银行流水和在职证明质量最高的版本。多页 PDF 要作为一等材料来源被接受，而不是拍照管线的附带产物。
- **并排比对。** 两栏并置 — 材料包文件对照生成它的 intake 数据，或生成的模板对照上传的证明材料 — 是手机给不了的审阅姿态。它同时服务于核对草稿的客户和做审核的运营者（§3.9）。
- **一屏看全文件树。** 材料包的结构 — 00 到 04，含 03 的六个证明材料文件夹 — 在一个视图里就能读完，而移动端必然要分页呈现。
- **直接打印与本地编辑。** 打印合订件可以直接从浏览器打印；DOCX 模板在本地 Word/WPS 里打开。把这条桌面路径明说出来，而不是让所有人都走手机的"发给打印店"流程（§3.8）。
- **intake 里的键盘效率。** Tab 顺序、回车进入下一步、每个字段都能粘贴、日期允许直接键入作为三字段控件的替代。一个打字熟练的用户应该能不碰鼠标走完一步。

对设计系统的后果：这些是同一批组件的变体，出自同一套 token 和同一份 `packages/core` schema — 不是第二套界面。

### 3.12 旅程中途跨设备

换设备是**用户的正常选择**，不只是 webview 被封锁时的绕行手段（§3.5）。"这部分我晚上回家用电脑填"、"用手机拍护照、在笔记本上收尾"、"在手机上看进度、在工位上打印"都是受支持的流程。

- **状态存在服务端，所以连续性是默认行为**（§3.2）。任何申请都能在任何设备上从离开时的那一步精确恢复，上传件、草稿和支付状态完整保留。
- **每个长步骤都有明确的"换设备继续"动作** — intake、上传页和交付页都有。它生成一个短时效签名链接（发到我邮箱／显示二维码供桌面用户用手机扫），落在同一步骤且已鉴权。微信逃生舱（§3.5）是这套机制的一个调用方，而不是它的定义。
- **把手机当作桌面会话的相机。** 停留在上传步骤的桌面用户可以显示二维码，用手机拍摄材料，并看着它们出现在桌面会话里 — 这是没有扫描仪时纸质材料质量最高的路径，而且它同时属于两端。
- **切换时绝不丢失工作。** 接力不会丢弃进行中的上传或未保存的答案；当一台设备重新连上一个正在别处编辑的申请时，显示服务端当前状态，而不是覆盖它。

## 4. 发布完成定义

- **每次发布跑设备矩阵：** 微信 iOS（WKWebView）、微信安卓（XWeb）、小红书 iOS 和安卓、Safari iOS、Chrome 安卓 — 在 375×667 和 390×844 下（E1）；外加桌面 Chrome、Safari、Edge，在 1280×800 和 1920×1080 下。这些 webview 没有一个能在桌面 devtools 里测。
- **每次发布冒烟测试五个脆弱流程：** 拍照采集加多页上传；网络中断下的断点续传恢复；支付到系统浏览器的接力；交付预览与打印合订件访问（含从桌面浏览器直接打印）；以及 intake 中途的跨设备接力（§3.12）能在同一步骤恢复。
- **每次发布，两种界面语言各跑一遍。** 设备矩阵在中文和英文下各跑一次 —— 布局按更长的那个字符串验证，且 intake 途中切换语言必须保留步骤、草稿和进行中的上传（[`internationalization-zh.md`](internationalization-zh.md) §9）。
- **重入性是构造出来的：** webview 被杀并重载后，用户回到同一步骤、状态已恢复，进行中的上传要么续传要么干净地重新提示；任何流程都不依赖跨一屏以上的内存状态。填 intake 填到一半去回聊天消息的用户是中位数会话，不是边缘情况。
